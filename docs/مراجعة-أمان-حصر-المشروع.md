# مراجعة حراسة المشروع والفروع

## نتائج مثبتة وإصلاحات

1. أعيد إنتاج حالة احترازية لبيانات مترابطة على نحو غير متسق: مشروع الفرع الرئيسي يحتوي بنداً يحمل صراحة فرعاً آخر. كان حفظ الحصر يستخدم القائمة الخام في عرض كل الفروع ويقبل السجل. أضيف حارس يرفض الحصر والمستخلص ومعاينة الإقفال إذا وُجد بند أو حصر أو مسودة أو محضر أو أمر تغيير مرتبط بالمشروع وله فرع صريح مختلف. يمتنع الحذف أيضاً عن محو هذا السجل. السجل القديم بلا فرع صريح يبقى مرتبطاً بالمشروع، ولا تُعدل بيانات العميل تلقائياً.
2. كان حذف مشروع بلا حركات مالية يحذف معه أمر تغيير حتى بعد اعتماد الأمر أو رفضه. يمنع الحذف الآن عند وجود أمر محسوم (`approved` أو `invoiced` أو `rejected`) حفاظاً على قراره وأثره التعاقدي؛ ما زال حذف مسودة أمر التغيير مع المشروع غير المرحّل ممكناً. لا يمس الإصلاح مشاريع أو سجلات سبق حذفها ولا يستعيدها.

الحراسة تكتشف التعارض **الصريح** في الحقول المدروسة ولا تثبت صحة جميع الروابط القديمة أو تعالجها. قفل الترحيل لا يشمل جميع الكتاب؛ لا تزال سباقات التخزين والاستيراد والاستعادة ومسارات خارج القفل تحتاج مراجعة مستقلة. سياق كل الفروع والصلاحيات والدفتر في الاختبارات بيئة Zustand/jsdom لا جهاز Windows العميل.

## الفحوص

اختبارات الفرع والحصر والمستخلص والحذف والمحضر 57/57، ثم اختبارات إضافية للتعارض الصريح في أربع مجموعات والسجل القديم بلا فرع: 46/46 في المجموعة الموجهة. `typecheck` و`lint:strict` ناجحان؛ `verify_engine_matrix` ‏43/43 بعد إعادة توليد المصفوفة. `audit:all` ‏19/19 وفحص تبعيات الإنتاج `npm audit --omit=dev` لم يُبلغ عن ثغرات معروفة عند الفحص؛ لا يعني ذلك خلو التطبيق من الثغرات أو فحص تبعيات البناء.
