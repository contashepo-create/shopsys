# مراجعة أولية للتواريخ والمشروعات

## ما تحقق

- فاتورة البيع والمشتريات المتقدمة: تاريخ مستند محلي اليوم افتراضياً، يسمح بالماضي؛ إدخال المستقبل محظور. وفي تعديل فاتورة مرحلة يعرض تاريخها الأصلي غير قابل للتعديل لأن إجراء التعديل لم يكن يحفظ تغيير التاريخ. إدخال الشراء السريع كان بلا تاريخ للمستند؛ أضيف حقل له، وأدخل في بصمة إعادة المحاولة.
- حارس `postSale` و`postPurchase` يرفض تاريخاً غير تقويمي أو مستقبلياً أو داخل سنة مالية مقفلة للفرع، قبل إنشاء طلب اعتماد أو قيد. الحظر أوسع من الفواتير الضريبية: كل فواتير البيع والشراء المصدرة، لأن الصفر الضريبي أو بيانات مورد لا تضمن التمييز الدقيق. تواريخ الاستحقاق والصلاحية ليست تواريخ إصدار ولا يشملها منع المستقبل. فواتير أُنشئت قبل الإصلاح لم تتغير.
- أمر تغيير المشروع يعرض تاريخ مستند افتراضه اليوم ويقبل تاريخاً تقويمياً سابقاً، ويحفظه مع وقت إنشاء فعلي منفصل عن وقت الاعتماد؛ لا ينشئ قيداً ولا يغير كمية. الاعتماد يؤثر فوراً مهما كان تاريخ المستند، ولا يمثل موافقة خارج النظام؛ يسمح التاريخ المستقبلي لأنه ليس فاتورة ضريبية ولا يؤجل الأثر. الأوامر القديمة لا تُمنح وقت إنشاء مخمَّناً.
- تاريخ القيد هو تاريخ المستند؛ ختم `createdAt` لقيد البيع وقيود/سجلات عمولته الجديدة هو وقت الإنشاء الفعلي. هذا لا يصلح الأختام القديمة ولا يثبت صحة أوقات الجهاز، ولا يراجع أختام باقي أنواع السجلات.

## أمثلة مؤكدة بلا مربع تاريخ معاملة — لم تُعدّل بعد

| النموذج | الدليل والسلوك | تنبيه قبل التطوير |
|---|---|---|
| دفعة مقدمة من العميل للمشروع | `ContractingPages.tsx` نافذة `advanceFor` واستدعاء `receiveClientAdvance` بلا تاريخ؛ المستودع يختم وقت التسجيل. | يترتب عليه تحصيل وقيد وعلاقة بالدفعات والاستردادات والفترات؛ يلزم حارس وترتيب وتدقيق وتواريخ فعلية للماكينة. |
| إصدار مستخلص مشروع | نوافذ إصدار المستخلص تستدعي `addProjectExtract` بلا تاريخ؛ في المستودع القيد والمستخلص يستعملان وقت التسجيل. | يتطلب حماية تسلسل الكميات والمستخلصات والسنة المقفلة وتاريخ التحصيل والتاريخ الفعلي لإنشاء القيد. |
| تحصيل وإقفال المحتجز | نافذة `releaseFor` تختار وسيلة التحصيل بلا تاريخ معاملة. | حركة مالية وغلق مشروع؛ لا يضاف حقل شكلي فقط دون ربطه بمسار القيد والتحصيل. |
| حصر المشروع | `ProjectSurveysPage.tsx` لا يعرض حقل تاريخ للحصر؛ `ProjectSurvey` يحفظ `createdAt` وأوقات المراجعات لا تاريخ قياس مستقل. | تاريخ القياس ليس تاريخ إنشاء السجل؛ يلزم تصميم الدليل والمراجعات وطباعة المحضر. |

هذه أمثلة فقط وليست جميع النماذج. بعد إضافة تاريخ أمر التغيير يعرض الفهرس 195 غلافاً و151 مرشحاً بلا تاريخ نصي. فهرس المرشحين الآلي في `docs/فهرس-أولي-لنماذج-التاريخ.md` يتضمن المسار والسطر لكل غلاف فُحص بلا حقل تاريخ نصي. لا يثبت الفهرس أنه يجب إضافة تاريخ لكل صف أو يغطي كل الواجهات. حصر جميع النماذج وتصنيفها وربط تواريخها بأعمالها المالية ما زال غير مكتمل.

## كميات المشروع وأوامر التغيير

- في المصدر الحالي، الحصر يرفض 1200 لبند كميته 1000، وكذلك حساب المستخلص الكمي التراكمي. الزيادة الواقعية لا تُسجَّل تلقائياً ولا تعني موافقة المالك.
- سقف المستخلصات هو إجمالي الأعمال قبل الضريبة للعقد الأصلي زائداً أوامر التغيير `approved` و`invoiced` ومخصوماً منها التخفيضات المعتمدة. `draft` و`rejected` لا تُضاف. آخر مستخلص يجوز أن يكون أقل من قيمة العقد؛ بعد الختامي لا يصدر مستخلص جديد.
- أمر التغيير مسجل كمبلغ إجمالي وليس مرتبطاً بكمية بند؛ اعتماده يرفع سقف القيمة لكنه لا يزيد كمية ذلك البند. تعديل كمية أو سعر بند له حصر محفوظ أو تنفيذ/مستخلصات ممنوع؛ الحل الآمن يحتاج تصميم اعتماد الزيادة وربطها بكميات البنود والتاريخ، لا مجرد رفع السقف أو محو أثر العقد القديم. يمكن دراسة بند إضافي منفصل بعد اعتماد نظامي وتأكيد اتساق العقد وأمر التغيير والتسعير، لا يُفترض ذلك تلقائياً.
- مثال قبل الضريبة: بند 1000 × 10 = 10000، ونفذ 1200 فعلياً. حتى مع أمر تغيير معتمد قدره 2000 يصبح سقف القيمة 12000، لكن حصر 1200 على البند الأصلي لا يزال مرفوضاً. لا ينشئ النظام موافقة صاحب العمل ولا يحسب قيمة الإضافي أو يغيّر كمية البند من واقع هذه الزيادة وحدها.
- هذا توصيف للمصدر في فرع الجلسة، وليس إثباتاً أن جهاز Windows ذي الإصدار 1.0.56 يحتوي نفس منطق الحصر الجديد. لم يُفحص جهاز العميل أو بياناته الفعلية.

## تعديل المشروع والسجلات

نافذة تعديل المشروع توسعت لتشمل الأقسام والبنود وإضافتها وحذفها، ومدير المشروع وتصنيفاته، مع حفظ المشروع والبنود في تحديث حالة واحد وحفظ معرّفات البنود القائمة. عند تغيير الجدول يُمنع ذلك احترازياً عند وجود حصر أو مسودة مستخلص أو أثر مالي أو تقدم أو محضر أو أمر تغيير محسوم أو رابط مهام/باطن؛ وتُمنع تغييرات الكمية والسعر لمشروع مرتبط بعرض فائز أو عند اختلاف العقد القديم عن مجموع البنود. يبقى تغيير بيانات عامة ممكناً حيث تسمح الحواجز. تراجع الصلاحيات والفروع والبصمة عند الحفظ داخل قفل مشترك للعمليات المتعاونة؛ فشل تأكيد التخزين بعد التحديث لا يعني التراجع. هذا محرر موسع وليس نسخة كاملة من واجهة إنشاء الفاتورة/المسودات؛ ولا يغلق كل المسارات القديمة المستقلة لتعديل البنود ولا يضمن عزل جميع الكتاب أو التبويبات.

سجل العميل أظهر خطأ renderer بقراءة `toLowerCase` من قيمة غير معرفة، لكنه بلا stack أصلي كافٍ لتحديد موضع المصدر؛ لم يُدّع إصلاحه. فحص تحديث GitHub أعاد 504 في السجل رغم وجود إصدار وملفاته حالياً؛ هذا لا يثبت سبب انقطاع الشبكة على الجهاز.

## نتائج الفحص في هذه الدفعة

- Vitest شامل: 366 ملفاً و2835 اختباراً ناجحة قبل تعديل توافق ختم الشراء؛ بعد هذا التعديل نجحت 27 حالة موجهة، بما فيها حالات التاريخ والشراء السريع ومسودات البيع. لم يُعَد الشامل بعد التعديل الأخير.
- `verify:all`: نجحت 351/351 بعد تعديل التوافق؛ typecheck وlint ناجحان، وlint به 147 تحذيراً. لا تثبت هذه الفحوص جهاز العميل أو مثبت Windows.
- أثناء فحص GitHub Actions للالتزام `51495c7` كانت مهمة سلامة قاعدة Windows والتحديث الصامت ناجحة، وفشل بناء مثبت NSIS قبل اختبارات التثبيت. يذكر تعليق المهمة HTTP 503 عند تنزيل Electron من GitHub؛ بقيت مهمتان جاريتين وقت الفحص. إخفاق سابق على `5f3233e` ذكر HTTP 504 للملف نفسه. هذا لا يثبت اكتمال CI أو نجاح تجربة تثبيت/ترقية فعلية.

## نتائج استكمال محرر المشروع وتاريخ أمر التغيير

- اختبارات محرر المشروع الموجهة 40/40، واختبارات تاريخ أمر التغيير وحذف غير المرحل 15/15. نجح فحص أنواع التطبيق والاختبارات وlint:strict. اختبارات الواجهة تستخدم قفل حفظ محاكياً؛ لا تثبت عزل كل كتاب التخزين أو تحقق الحفظ على جهاز العميل.
- فهرسة التواريخ وتصنيفها لم تكتمل: الدفعة والمستخلص والمحتجز والحصر وغيرها ما زالت بلا تاريخ معاملة مدخل، ولا يُنصح بربط تاريخها بالقيود بلا حراسة للفترات والتسلسل. لا نشر عام في هذه الدفعة.
