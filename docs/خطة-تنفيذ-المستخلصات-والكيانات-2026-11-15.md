# خطة تنفيذ نطاق المستخلصات والكيانات والقوائم

تاريخ البدء: 2026-11-15. هذه قائمة متابعة للنطاق المطلوب وليست حصرًا لعيوب النظام. لا تُعلّم مرحلة مكتملة إلا بعد تنفيذ مساراتها واختبارها على رأس التغييرات وإثبات الاعتمادات الخارجية اللازمة. تُسجل كل جولة أدناه مع حدودها؛ لا تعني علامة إنجاز مهمة فرعية إنجاز المرحلة.

## ترتيب التنفيذ ومعايير القبول

- [ ] **1. التخزين وأدلة التاريخ:** حصر الكتّاب والمخازن والأقفال والدمج والاستعادة؛ تصميم حماية مشتركة وذرية القيود والفترات أو رفض الحالات التي لا يمكن ضمانها؛ حماية الأرقام وعدم إحياء المحذوفات؛ اختبارات SQLite الفعلي والكتابة المتزامنة وفشل الحفظ والنسخ القديمة والجديدة. تحديد حدود الأجهزة المدعومة صراحة.
- [ ] **2. إشعارات المستخلصات:** إدخال المقدمة المعادة يدوياً، وحدود وتوزيع مثبت لكل دفعة، وإعادة تشغيل التاريخ والقيد المتوازن والتقارير مع اختبارات الذمة والنقد والماكينة والضريبة والمحتجز والاستعادة. لا يفعّل الموجب قبل اكتمال التسلسل والأدلة.
- [ ] **3. المحتجز المحصّل:** إثبات تخصيص التحصيل للمستخلصات، وعكسه أو تسويته ورفض القديم المجهول؛ اختبار الجزئي والمتعدد والتاريخ والتزامن والاستعادة.
- [ ] **4. التوثيق والتحصيل المعقد:** تخصيص الفواتير والمرتجعات المشتركة، وأدلة التصحيح الضريبي الخارجي، ومنع ازدواج التحصيل أو الرد؛ تسوية الذمة والخزينة والماكينة وربطها بالأصل. إيقاف الحالات المجهولة للمراجعة البشرية.
- [ ] **5. إعادة فتح الختامي والبديل:** حدث فتح بصلاحية وسبب، حفظ التاريخ، تدقيق الكميات والإشعارات والتوثيق والمحتجز والمقدمة والتحصيل والعقد وأوامر التغيير، اعتماد حصر يدوي، ثم مستخلص بديل مترابط ومرقم؛ اختبار الحالات القديمة والتزامن والاستعادة.
- [ ] **6. حذف المشروع المرحّل:** جرد جميع الآثار بما فيها المشتركة والمخزون والقيود، معاينة وبصمة خام وإعادة فحص، رقم المالك فقط وسبب وتدقيق، والسماح بالفترة المقفلة. اعتماد تصميم ذري متوافق مع دفتر SQLite ذي الإلحاق فقط، وحماية الأرقام والاستعادة؛ رفض كل رابط مشترك أو غير قابل للفصل. لا يُزال الحارس الحالي قبل ذلك.
- [ ] **7. عزل الكيانات:** بيانات وهوية الكيان والمكلف، تأريخ علاقة الفروع، سياسة للقيود غير المنسوبة والافتتاحيات والمشترك، عزل الترحيل والصلاحية والتقارير والاستعادة، وسياسة نقل الفرع؛ التفريق بين الفرع والكيان والشامل والتوحيد القانوني. الإطار والإعفاء يحتاجان مراجعة مختص.
- [ ] **8. القوائم والإقفال:** تصنيفات وسياسات مؤرخة لكل إطار، قوائم مقارنة وتغير حقوق الملكية وإيضاحات، مراجعة الاستحقاقات والجرد والبنوك والذمم والضرائب والافتتاحيات، أدلة المعاملات البينية والتدفقات المركبة؛ عرض التحذيرات حتى الاعتماد.
- [ ] **9. قوائم والزكاة:** تحديد النماذج والتصنيفات واللوائح الرسمية السارية ونوع المنشأة والمكلف والتفويض والمرفقات، ثم تصميم التحقق والتصدير والإيصالات والتصحيحات؛ التكامل فقط بواجهة رسمية وتصريح واختبار قبول فعلي. لا تُحسب الزكاة كنسبة آلية من الربح. لا أسرار بالمستودع.
- [ ] **10. الاختبارات والإصدار:** اختبارات الوحدات والواجهة والتكامل والتقريب والتواريخ والقديم والتالف والتزامن والاستعادة وSQLite؛ Windows والترقية والطباعة؛ الأنواع وlint:strict والبناء وverify:all وtest:e2e وبوابة GitHub على الرأس النهائي، ثم مراجعة مختص واختبار جهاز العميل قبل قرار الإصدار. لا رفع رقم إصدار لمجرد بدء العمل.

## إضافات المالك: واجهة المقاولات والعملاء ومراجعة المشروع

- [ ] استبدال رموز إرسال واتساب للمستندات بشعار واضح موحد، مع إبقاء إرسال تليجرام وإجراءات تقديم المستند مستقلة، واختبارات للعرض والوظيفة.
- [x] معالجة مسافة عنواني العميل المسجّل و«ساري حتى» عن مدخلاتهما في محرر عروض الأسعار، واختبار أحجام العرض وعدم كسر بقية الفاتورة **محلياً**؛ اختبار جهاز العميل والمتصفحات الأخرى ما زال ضمن المرحلة 10.
- [ ] تصميم أنواع العملاء وجهة اتصال المسؤول ووسائلها اختيارياً ومتوافقة مع القديم، وحفظها والتحقق منها وتحريرها؛ ثم دعم جهة اتصال عرض السعر والمشروع وتاريخ المستندات دون افتراض جهة قديمة.
- [ ] تصميم إسناد الموظف لمشروع واحد أو أكثر بتاريخ ونسبة أو ساعات معتمدة، وحساب وتوزيع الرواتب على المشاريع والفرع دون تكرار القيد أو احتساب راتب غير معتمد، ومعالجة تغيير التخصيص والختامي والاستعادة والتزامن. يتطلب اعتماد أساس التكلفة ومعالجة الوقت والمستحقات قبل الترحيل.
- [ ] مراجعة أقسام المقاولات ووظائفها مقابل الأدلة والاختبارات، وتوثيق الفجوات مقارنة بوظائف أنظمة إدارة المقاولات المعروفة بمصادر قابلة للتحقق؛ لا تُدّعى مراجعة شاملة بمجرد فحص أسماء الصفحات.
- [ ] مراجعة حالة وإجراءات إقفال المشروع وعلاقتها بالختامي والذمم والمحتجز والمقدمة والالتزامات والتكاليف؛ اختبار الرفض والتسلسل والتقارير وتوثيق ما يثبته الإقفال وما لا يثبته.
- [ ] تدقيق دورة صرف المواد وتكلفتها وقيود المخزون وربح المشروع والتواريخ والكسور والاستعادة والتزامن، وتدقيق ملفات العهدة والتمويل والصرف والتسوية والزيادة وروابط المشروع والمخزن والفرع والتقارير؛ اختبار الحالات السليمة والتالفة والمشتركة.
- تُراجع التعديلات المهمة واختباراتها بعد تنفيذها، وتبقى بنود الطلب الأصلي مفتوحة حتى تحقيق معاييرها؛ لا إصدار أو اعتماد مالي اعتماداً على التحسينات الشكلية.

### الجولة الثانية — حراسة استعادة حالة الإقفال واختبار SQLite
- [x] يمنع فحص استعادة الإقفال الآلية إصلاح السنة المفتوحة إن ظهر في ترتيب اليومية المحفوظ بعد قيد إقفال نشط قيدٌ للفرع نفسه ضمن الفترة، أو تاريخ غير صالح للفرع؛ ويمنع مسار المستودع إعادة الفتح أو استعادة الإقفال في الحالة نفسها دون تغيير القيد أو الحالة. الأنشطة المثبتة في فرع أو سنة أخرى لا تحجب؛ الفتح ثم التصحيح وإعادة الإقفال تبقى ممكنة.
- [x] اختبار كاتبين للتعارض مع الصلاحية على ملف SQLite حقيقي والتحقق من اللقطة والجدول واليومية بعد إعادة فتح الملف، وحقن فشل داخل معاملة حفظ لقطة منفردة والتحقق من التراجع. ليست هذه اختبارات أجهزة متعددة أو معاملة بين المخزنين.
- [x] الأنواع و`lint:strict` والبناء ناجحة مع تحذير حجم الحزمة؛ اختبار موجه للإقفال 33/33، واختبار SQLite الجديد 2/2، ثم `test:e2e` ‏3550/3550 في 464 ملفاً. فشل `verify:all` أولاً بسبب المصفوفة؛ أُعيد توليدها ونجحت بوابتها 43/43 ثم نجح `verify:all` ‏351/351. لم تُختبر GitHub أو Windows أو جهاز العميل لهذه الدفعة.
- الحارس يعتمد ترتيب المصفوفة المحفوظة لا دليلاً زمنياً مستقلاً؛ قد لا يكشف حركة متزامنة دُمجت قبل قيد الإقفال، ولا يفحص كل حالات تلف التاريخ أو يضمن منع إقفال أو ترحيل كاتب لا يشارك القفل. لا يزال حفظ الفترة والدفتر في مخزنين منفصلين. لا تعني الاختبارات إصلاح التزامن الشامل أو انتهاء المرحلة الأولى.
- التالي: تصميم حراسة مشتركة وذرية لمخزن الإقفال واليومية، ومسار واضح لفشل الحفظ وتعارضات الاستعادة قبل تفعيل تسويات مالية جديدة.

### الجولة الثالثة — علامة عكس اليومية وإعادة محاولة SQLite
- [x] ترسل كتابة لقطة سطح المكتب القيد الأصلي الذي اكتسب علامة عكس جديدة مع القيد العاكس، بعد التحقق من رابط `reversesEntryId` الفريد؛ يحفظهما SQLite مع اللقطة في معاملة واحدة. إذا كان الأصل موجوداً في الجدول فلا يُغيّر رقمه أو تاريخه أو سطوره أو هويته، ولا تُستبدل علامة عكس مسجلة بعلامة أخرى؛ التعارض يوقف المعاملة للمراجعة.
- [x] إعادة محاولة بنفس مفتاح الحفظ لا تُعد نجاحاً إلا إذا طابق المحتوى والمراجعة الحفظ الأخير. اختُبر نجاح الإعادة بعد ضياع الرد، ورفض محتوى أو مراجعة مختلفين، وفشل كتابة العكس وتراجع اللقطة والأصل والقيد، والاختلاف التاريخي للأصل، وإعادة فتح ملف SQLite.
- [x] نجح محلياً 70 اختباراً موجهاً، و`test:e2e` ‏3556/3556 في 464 ملفاً، و`verify:all` ‏351/351، والأنواع و`lint:strict` والبناء. نجح `desktop:compile` لكن لم يكن ثنائي Electron متاحاً لتوليد bytecode؛ ظهر تحذير حجم الحزمة. لم تُختبر بوابة GitHub أو Windows أو جهاز العميل لهذه الدفعة.
- الحدود: التحقق من الرابط وحده لا يثبت صحة أطراف القيد العاكس؛ لا تُصلح العلامات القديمة الناقصة تلقائياً ولا تُراجع جميع السجلات التاريخية. الجدول المسطح لا يحمل جميع أبعاد القيد، والمطابقة تقع للقيود المرسلة فقط؛ الحارس ليس منعاً شاملاً للكتابة المباشرة أو حذف المشروع أو الاستعادة. الاستعادة JSON ما زالت تكتب مخزن الإعدادات ثم البيانات منفصلين، واستعادة ملف قاعدة قد تستبدل السجل كاملاً؛ يلزم تصميم ذري ومراجعة حماية إحياء المحذوفات والأرقام قبل اعتبار الاستعادة آمنة لهذا النطاق.
- التالي: تصميم معاملة استعادة/إقفال مشتركة وتدقيق دفاتر SQLite التاريخية دون اختلاق دليل، ثم متابعة تسويات المقدمة والمحتجز حسب تبعيات الخطة.

### الجولة الرابعة — حراسة سجل الحذف عند استعادة JSON والمزامنة

- الحدود: الفحص يخص سجلات حذف المشاريع الموجودة محلياً والروابط التي يعرفها، ولا يحصر كل الروابط غير المباشرة أو يضمن مزامنة الحالة مع كل الكتّاب والأجهزة. لا يشمل استعادة ملف SQLite كاملاً، ولا يجعل كتابة مخزني JSON ذرية بعد اجتياز الفحص، وقد يتطلب مراجعة بشرية عندما تكون النسخة أقدم من سجل الحذف. حذف المشروع المرحّل ما زال محجوباً.
- التالي: معالجة تعارض الاستعادة والكتابة وذرية المخزنين قبل رفع أي حظر، ثم متابعة أدلة التسويات والعمليات المالية وفق الترتيب.

- `getProjectPayrollCosts` يقرأ توزيع القسائم من الحالة الخام ويقارن الأدلة بالبيانات الظاهرة، ويتحقق من فرع المشروع والقسائم ومجموعة القيد والإلغاء، والنسخ المكررة والقيود والارتباط بتكلفة أخرى. ربط `getProjectProfit` توزيعات القسائم النشطة المثبتة بفئة العمالة؛ الملغاة تُستبعد بعد التحقق من قيد إلغائها فقط. لا ينشئ ذلك `projectCosts` ولا قيداً ثانياً، والمرجع هو تكلفة 5102 = صافي الراتب + السلفة المستردة. يتحقق تجميع الربحية وتكاليف المشروع من النطاق العددي ومن تطابق إجمالي المستند مع بنوده.

- عند تعذر مطابقة التوزيع أو قيده أو الإلغاء تُحجب مؤشرات الربحية وتقارير المقاولات المتأثرة بدلاً من استبعاد القسيمة بصمت. تُرفض القسيمة الملغاة القديمة التي لا تملك مرجع إلغاء، كما يرفض الفحص تحفظياً وجود قسيمة أخرى لنفس الموظف والشهر ولو كانت ملغاة؛ إعادة إصدار سليمة بعد إلغاء قد تحتاج مراجعة ولم تُبنَ آلية آمنة لمعالجتها هنا. القسائم أو المسيرات بلا توزيع لا تُستنتج لها مشاركة ولا تدخل الربحية؛ تنبه الواجهة والمطبوعات والصادرات إلى ذلك. تختلف موازنة المشروع وEVM حالياً: تعتمد مستندات تكلفة المشروع ولا تتضمن توزيع 5102 أو مرتجعات الشراء، وتوضح الشاشات هذا القيد.
- اختيار مشاركة الموظف لا يزال يدوياً لكل شهر، مع اقتراح متساوٍ وتعديل قبل إصدار القسائم؛ لا يوجد سجل مشاركة مؤرخ يتكرر تلقائياً، ولا يدعم المسير المجمّع هذا التوزيع. لا يثبت فحص القيود حدوث مشاركة فعلية أو يكشف كل تسوية مستقلة أو تكرار محاسبي قُيد بقيد آخر. حدود عزل الفروع، الاستعادة والمزامنة والكتّاب المتزامنين، ونقص التاريخ القديم، واعتماد المحاسب، واختبار Windows/Electron وأجهزة متعددة باقية. نجاح هذه الشريحة ليس اكتمالاً للبنود الخمسة عشر أو إعلان جاهزية إصدار.
- **التحقق لهذه الدفعة:** نجحت 80 حالة موجهة في سبعة ملفات، وأنواع الاختبارات و`lint:strict` و`build`، و`desktop:compile` مع تخطي bytecode لغياب ثنائي Electron. بعد تحديث بوابة نصية قديمة كانت تفترض ظهور صافي 5110 وحده في بطاقة المصادر، نجح `verify:all` ‏351/351؛ كانت المحاولة الأولى قد فشلت في تلك البوابة فقط. تشغيل `test:e2e` لم ينجح بالكامل: 3921/3922 و496/497 ملفاً؛ فشل اختبار انتظار حذف مسودة بيانات المنشأة بعد الاستعادة المتأخرة (`company_profile_page.test.tsx:111`) لأن المسودة بقيت عند انتهاء الانتظار. نجح ملفه منفرداً 13/13، لكن ذلك لا يثبت سبب الفشل ولا يُعد نجاحاً للتشغيل الشامل. يلزم تقصي التوقيت/الحفظ وإعادة تشغيل الشامل قبل الاعتماد.

### متابعة الموازنة وEVM مع حصص قسائم الرواتب
- تُضاف حصة المشروع من قسائم 5102 المثبتة إلى عمالة الموازنة وإلى التكلفة الفعلية في EVM، دون إنشاء قيد أو تكلفة مشروع جديدة. يستثنى الإلغاء بعد التحقق من قيده، وتحجب الأرقام عند عدم مطابقة أدلة التوزيع أو المبالغ؛ يحافظ الجرس على بقية التنبيهات ويعرض مراجعة للمشروع، وتوضح نافذة المصروف أن تعذر الحساب لا يعني عدم التجاوز. تتحدث الشاشات والجرس عند تغير الأدلة ذات الصلة.
- النطاق استرشادي: مرتجعات الشراء لا تخصم في الموازنة وEVM، والمسير المجمّع والقسائم غير الموزعة لا تدخلان الحساب، كما لا يثبت الفحص المشاركة الفعلية أو اكتمال جميع التكاليف. لا يجوز وصفه بصافي تكلفة دفترية أو اعتماد مالي. سجل المشاركة الشهري والمسير المجمّع وإعادة إصدار قسيمة بعد إلغاء مثبت ما زالت غير مكتملة.
- نجحت أنواع التطبيق والاختبارات و`lint:strict`، والتشغيل الشامل `test:e2e` ‏3927/3927 في 497 ملفاً. نجح كذلك اختبار نافذة المصروف الإضافي بعد التشغيل الشامل ضمن ملف تكامل 10/10. اختبار مسودة المنشأة الذي فشل سابقاً نجح في التشغيل الحالي والموجه، لكن لم يُثبت سبب الفشل السابق ولم تُعالج احتمالات التسابق منهجياً. لا يُعد ذلك ضماناً بعدم تكراره. لم يُختبر Windows/Electron الحقيقي أو تزامن الأجهزة ولا يوجد اعتماد إصدار.
- أُعيد توليد مصفوفة المحرك؛ نجح `verify:all` ‏351/351 و`build` مع تحذير حجم الحزم. لم يُشغّل `desktop:compile` لهذه الدفعة.

### متابعة إعادة القسيمة بعد إلغاء مثبت
- يمكن إصدار قسيمة جديدة لنفس الموظف والشهر بعد فحص قسائمه السابقة ومجموعات استحقاقها وأدلة الإلغاء الظاهرة، حتى إن كانت القسيمة السابقة بلا توزيع. تتحقق القراءة من مجموعات التاريخ المتصلة، وتستبعد الملغى بعد مطابقة القيود، وتحسب البديلة وحدها للمشروع؛ تتوقف عند تكرار نشط أو دليل مفقود أو غير مطابق. تشترط المقارنة ترتيب معرفات القيود المحلية وتواريخها بين الإلغاء والاستحقاق التالي؛ هذا فحص محافظ قد يرفض تاريخاً مستورداً لا يحافظ على التسلسل، وليس إثباتاً شاملاً للتزامن أو الزمن الفعلي.
- لا يُسمح باستبدال قسيمة موزعة ملغاة بمسير مجمّع، لأن ذلك المسار لا يدعم تخصيص المشاريع وفحصه؛ تستبعده واجهة المسير الظاهرة وتوجه للقسيمة البديلة. المسير المجمّع بعد قسيمة غير موزعة يتحقق من الإلغاء بدلاً من الاعتماد على حالتها فقط. القسائم المخفية في فرع آخر أو أدلتها غير الظاهرة تتطلب مراجعة ولا تُكشف تفاصيلها.
- يحمي حارس تاريخ التوزيع القسائم غير الموزعة لنفس الموظف والشهر عندما تكون جزءاً من تاريخ قسيمة موزعة، ويمنع إسقاط أساسها أو مرجع إلغائها المعروف في مسارات الاستعادة المحمية. أضيفت تكاليف المشروع لأساس تعارض دمج المسير وبصمة واجهة القسائم. الحواجز لا تثبت اكتمال الأدلة الجديدة ولا تمنع كل كاتب أو تعارض جهاز فعلي، ولا تعالج التاريخ التالف تلقائياً.
- نجح `test:e2e` ‏3938/3938 في 497 ملفاً؛ ثم أضيف اختبارا ترتيب القيد والفرع المخفي ونجح ملف القسائم 31/31. نجحت أنواع التطبيق والاختبارات و`lint:strict`. لم يُختبر Windows/Electron الحقيقي أو تزامن أجهزة فعلي ولا يوجد اعتماد مالي؛ سجل المشاركة الشهري والمسير المجمّع الموزع وخصم المرتجعات في الموازنة وEVM ما زالت مفتوحة.
- نجح `verify:all` ‏351/351 بعد توليد مصفوفة المحرك، ونجح `build` مع تحذير حجم الحزم. لم يُشغّل `desktop:compile` لهذه الدفعة.

### مراجعة مرتجعات مشتريات المشروع قبل إكمال الموازنة وEVM
- **تصحيح للتوصيف السابق في هذه الخطة:** فحص مسار الشراء كشف أن فاتورة المشروع تُحمّل 5110 مباشرة ولا تدخل مخزون المتجر، وأن `postPurchaseReturn` يمنعها؛ قيد المرتجع المخزني العام يعكس 1103 لا 5110. لذلك كان خصم أي مرتجع مستورد لمجرد ارتباطه بفاتورة مشروع، أو الادعاء بأنه يعكس 5110، استنتاجاً غير مثبت. لا يمكن الاستنتاج من ذلك وحده صحة أي تسوية مورد أو ضريبة أو وجود بضاعة يمكن إرجاعها.
- أصبح تفصيل تكاليف المشروع يفحص المرتجعات المرتبطة بفواتير المشروع في البيانات الخام حتى لو كانت مخفية في الفرع، ويوقف الربحية وتقارير المقاولات والموازنة وEVM للمراجعة بدلاً من خصم المبلغ أو عرض رقم ناقص. تعرض الواجهات والجرس سبب المراجعة ضمن نطاق التحذير؛ المرتجع غير المرتبط بالمشروع لا يوقفه. لا يعد ذلك معالجة أو إثباتاً لسجل مستورد، ولا يضمن اكتشاف فاتورة مفقودة أو علاقة تالفة غير قابلة للاستنتاج.
- لم يعد رفض المرتجع المخزني يوجّه المستخدم إلى تسجيل سند قبض كحل مفترض؛ يلزم فحص تسوية المورد والتكلفة والضريبة. صُحح دليل المستخدم وعناوين المصادر لتجنب ادعاء مطابقة كامل الدفتر. ما زال تصميم وترحيل مرتجع مشروع فعلي وتخصيص الكميات والمصاريف والضريبة والمورد وتدقيق 5110 التاريخي والاستعادة والتزامن غير منفذ؛ لا يُزال الحظر دون هذه الأدلة. سجل المشاركة الشهري والمسير المجمّع الموزع ومراحل الخطة الأصلية والاعتمادات الخارجية لا تزال مفتوحة.
- نجحت 68 حالة موجهة قبل الاختبار الواقعي الإضافي، ثم نجح ملف التكامل 14/14 مع فاتورة مشروع حقيقية ورفض المرتجع دون تغيير، ونجح `test:e2e` ‏3944/3944 في 497 ملفاً. الأنواع و`lint:strict` ناجحة؛ الفشل الأول لاختبار واجهة جديد كان نتيجة إرجاع وعد `setState` من `act` دون انتظاره، وصُحح جسم الاختبار وأعيد بنجاح. لم يُختبر Windows/Electron أو أجهزة متعددة فعلياً ولا يوجد اعتماد مالي.
- نجح `verify:all` ‏351/351 بعد إعادة توليد المصفوفة، و`build` مع تحذير حجم الحزم؛ لم يُشغّل `desktop:compile` لهذه الدفعة.

### متابعة طلب خمس مراحل — أدلة تحصيل المحتجز وتعارض اللقطات (جزئية)
- التحصيلات الجديدة تحفظ نسخة حساب الخزينة ونسخة حركة الماكينة إن وجدت داخل سجل التحصيل. يفحص رصيد المحتجز والربحية مطابقة الحساب مع القيد، ومطابقة الحركة المحفوظة مع الحركة الحالية ومبلغها ومصدرها ووقتها، ويرفضان الحركة المفقودة أو المكررة أو المعدلة أو المردودة/الملغاة للمراجعة. التحصيل الجديد بلا ماكينة يرفض وجود حركة تحصيل ماكينة مرتبطة به. لا يفترض هذا الدليل تفاصيل سجلات قديمة ولا يثبت التسوية البنكية أو إثبات المزود الخارجي.
- يحافظ حارس تاريخ المشاريع على حركة الماكينة المرتبطة بتحصيل محلي موثق في مسارات مقارنة اللقطات والاستعادة المحمية؛ ودمج اللقطات يرفض إصدار التحصيل بالتزامن مع تغييرات أساس المشروع والحركات المالية أو الصلاحيات ذات الصلة، بالاتجاهين. الاختبار لمحاكاة دمج لقطة وليس تزامن جهازين، والحراسة لا تقفل مخزن الفترات المستقل ولا تمنع كاتباً خارج هذه المسارات. قد تتطلب الاستعادة من نسخة أقدم مراجعة بدلاً من إسقاط الدليل.
- لا توجد بعد تخصيصات تحصيل المحتجز للمستخلصات أو عكس/تسوية متكاملة أو معالجة للسجلات القديمة مجهولة الأصل؛ ولا تُزال القيود على رد المقدمة أو إعادة فتح الختامي. لم تنجز مراحل التخزين والإشعارات والمحتجز والتوثيق والختامي الخمس بمعاييرها، وتبقى مربعاتها مفتوحة.
- نجح 82 اختباراً موجهاً ثم `test:e2e` ‏3964/3964 في 497 ملفاً، وأنواع التطبيق والاختبارات و`lint:strict`. فشلت المحاولة الأولى لـ`verify:all` في بوابة المصفوفة المتقادمة وحدها؛ بعد توليدها نجح `verify:all` ‏351/351. نجح `build` مع تحذير حجم الحزم و`desktop:compile` مع تخطي bytecode لغياب Electron. لم يُختبر Windows أو تزامن أجهزة حقيقي ولم يُعتمد التصميم مالياً أو للإصدار.

### متابعة — إثبات حصة المستخلص من تحصيل المحتجز الكامل
- عند تحصيل كامل المحتجز للمرة الأولى، تُحفظ في سجل التحصيل حصة كل مستخلص وقيده الأصلي بعد خصم محتجز الإشعارات الكمية المثبتة السابقة؛ مجموعها يساوي قيد التحصيل ولا ينشأ قيد إضافي. يعيد فحص رصيد المحتجز والربحية حساب التوزيع عند قيد التحصيل بعد مراجعة المستخلصات والإشعارات والقيود وتسلسلها، ويحجب القيمة إن فُقد أو تبدل التخصيص أو اختلف مجموعه. لا يُعاد بناء التوزيع للمستخلصات التي لم تكن قد صدرت حين التحصيل.
- لا يخمّن النظام حصة المتبقي بعد تحصيل سابق مجهول: يرفض تحصيلاً جديداً عند وجود تحصيل سابق ويتطلب مراجعة. تبقى السجلات القديمة دون تخصيص كما هي، ولا يضيف إليها الدليل تلقائياً؛ القراءة الحالية لبعض أرصدتها الإجمالية لا تعني إثبات توزيعها. لا يُرفع حظر الإشعار بعد التحصيل: لم تُنفذ تسوية أو عكس أو تحصيل جزئي أو إعادة فتح الختامي، ولم تُعتمد المعالجة مالياً. الحراسة عند قراءة الرصيد ليست تحققاً مسبقاً لجميع اللقطات الواردة أو الكتّاب.
- حماية تاريخ التحصيل تمنع إسقاط أو تعديل التخصيص المحفوظ في مسارات مقارنة اللقطات؛ اختُبرت نسخة SQLite فعلية مطابقة وتغيير حصة بمبلغ مماثل إلى مستخلص آخر، ونسخة JSON وإعادة الترطيب، وتحريف التخصيص وحالة مستخلصين وإشعار سابق وتحقيق الباقي بعد تحصيل قديم، بالإضافة لاختبارات تعارض اللقطات الموجهة. لا يثبت اختبار SQLite تزامن أجهزة أو صلاحية كل البيانات المستوردة.
- بعد توليد المصفوفة نجح `verify:all` ‏351/351، و`test:e2e` ‏3968/3968 في 498 ملفاً، وأنواع التطبيق والاختبارات و`lint:strict` والبناء مع تحذير حجم الحزم و`desktop:compile` مع تخطي bytecode لغياب Electron. المراحل الخمس ما زالت مفتوحة، ولا اختبار Windows/أجهزة حقيقية أو اعتماد مالي أو إصدار.

### متابعة طلب عشر مراحل — حماية أساس تحصيل المحتجز (عمل جزئي)
- في مقارنة التاريخ المحمية، أصبح التحصيل ذو التخصيص المحفوظ يحافظ على مستخلصاته الأصلية وأسسها، بما فيها المستخلص السابق الذي صفّت إشعاراته المحتجز، ويرفض إدخال مستخلص محتجز مؤرخ قيدُه قبل قيد التحصيل بأثر رجعي. يتحقق الحارس من شكل الحصص وروابطها ومجموعها؛ لا يحل ذلك محل الفحص المحاسبي الكامل عند قراءة الرصيد. اختُبر إسقاط الأصل أو تعديله عبر SQLite والاستعادة ولقطات السحب والتعارض والدمج بالاتجاهين، إلى جانب الحالة المطابقة.
- يمنع مسار تسجيل حركات الماكينة العام رد أو إلغاء حركة مرتبطة بتحصيل محتجز منفردة، بما فيها حركة قديمة مرتبطة برقم مستند التحصيل. تحمي مقارنة التاريخ أيضاً من تغيير ردود الحركة التي يحمل التحصيل دليلاً محفوظاً لها، دون ادعاء إصلاح رد تاريخي أو حماية كل مسار كتابة. أضيف اختبار سحب سحابي يرفض الرد المستقل. لا يوجد عكس متكامل لقيد المحتجز وحالة المشروع أو تسوية مزود الدفع.
- تعرض تفاصيل المشروع حصص التحصيل المدققة وقيد كل مستخلص، أو تنبه إلى عدم وجود تخصيص محفوظ للتحصيل القديم، وتحجب التفاصيل عند تعذر مراجعة الربحية. لا يثبت العرض التحصيل البنكي أو سلامة كل البيانات القديمة. تقارن نافذة التحصيل الآن بصمة محافظة لأدلة إضافية بينها القيود الخام والماكينات والخزائن والصلاحيات والفترات قبل الترحيل؛ قد ترفض تغييراً غير متعلق بالمشروع، ولا تقفل مخزن الإعدادات المستقل أو كاتباً خارج المسار أو أجهزة أخرى.
- لم تُنجز عشر مراحل مكتملة: ذرية التخزين والمزامنة، إشعارات المستخلصات واسترداد المقدمة، التحصيل الجزئي والعكس، التسوية الضريبية وإعادة فتح الختامي ما زالت تحتاج التصميم والتنفيذ والاختبار والاعتماد. لا يُرفع حظر الإشعار بعد التحصيل؛ لا يُستنتج تخصيص تاريخي مجهول، ولا يعتبر نجاح هذه الاختبارات اعتماداً مالياً أو إثباتاً لتسوية البنك أو اختبار Windows/Electron وتزامن أجهزة فعلياً.
- **التحقق:** نجحت اختبارات موجهة 169/169 في سبعة ملفات قبل إضافة اختبار السحب الأخير، ثم نجح ملفا السحب والأدلة 59/59. نجح `test:e2e` ‏3986/3986 في 498 ملفاً، وأنواع التطبيق والاختبارات و`lint:strict` و`verify:all` ‏351/351 بعد إعادة توليد المصفوفة، و`build` و`desktop:compile` و`git diff --check`. بقي تحذير حجم الحزم وتُخطي توليد Electron bytecode لغياب ثنائي Electron في البيئة.

### متابعة طلب 15 مرحلة — سلامة معرّفات اليومية ودمجها (جزئية)
- أصبح فحص مقارنة اليومية يرفض معرّف قيد مكرراً أو غير صالح في أي موضع من اليومية الواردة، حتى إذا كان دفتر الجهاز المحلي فارغاً، مع إبقاء قبول النسخة القديمة التي لا تحمل اليومية عندما لا يوجد دفتر محلي. يتكامل ذلك مع المسارات التي تستدعي الفحص بالفعل: استعادة JSON وSQLite الملفية وسحب السحابة ولقطة التعارض. فحص المعرف وحده لا يثبت توازن القيود الجديدة أو صحتها أو اكتمالها.
- أُضيفت مقارنة الدفتر الناتج من دمج لقطات سطح المكتب مع أساس وكل طرف، بعد حراسات التعارض المتخصصة؛ فلا تُركب بيانات قيد من تعديلين متزامنين، ولا يُقبل إسقاط أو تغيير سجل طرف أو ترتيب يخالف امتداد تاريخه. يقبل إضافة واحدة وعكساً مثبتاً مع تغيير مستقل، لكنه يرفض تحفظياً إضافتين مختلفتين للدفتر في الطرفين حتى عندما يمكن للمحاسب تسويتهما، ويتطلب إعادة التحميل والمراجعة. اختُبرت هذه الحالة بكاتبين وSQLite حقيقي وإعادة فتح القاعدة، وليست اختبار أجهزة فعلية أو كل كتّاب SQLite.
- يُشترط تطابق فرع الأصل والعاكس، بما في ذلك وجود الفرع في أحدهما دون الآخر، عند استخراج القيود لتسجيل علامة العكس في SQLite؛ اختُبر الرفضان مع ثبات اللقطة والجدول. لا يثبت ذلك صحة جميع العكوس القديمة، والجدول المسطح لا يحمل جميع أبعاد القيد.
- هذه الحراسات لا تجعل مخزني البيانات والإعدادات ذريين ولا تمنع كاتباً يتجاوز المسارات المعنية. فحص الدمج يعمل عند تعارض المراجعة، وليس فحصاً شاملاً لكل حفظ مباشر؛ مسار استخراج القيود للحفظ غير المتعارض لا يضمن بحد ذاته حماية كل تعديلات وحذف تاريخ اليومية في لقطة JSON. يجب جرد مسارات الكتابة والبيانات القديمة ووضع سياسة مراجعة واختبارات قبل تعميم حارس دفتر الإلحاق على كل حفظ. لا يُرفع حظر الإشعار بعد التحصيل، ولا تعد الجزئي أو عكس المحتجز أو المقدمة أو الضريبة أو الختامي أو التخزين مكتملة، ولم تُنجز 15 مرحلة مكتملة.
- **التحقق:** نجحت اختبارات موجهة 151/151 في ستة ملفات، ثم 70/70 في خمسة ملفات بعد نقل فحص اليومية إلى ما بعد حراسات تعارض الإقفال، وتشمل SQLite حقيقياً. التشغيل الشامل الأول فشل 5 حالات في 4 ملفات؛ منها حالتا إقفال بسبب أسبقية رسالة الحارس، واختبار واجهة مرتجع شراء انتهى دون رسالة عند الانتظار. بعد تعديل موضع الحارس نجحت الملفات الموجهة والإعادة الشاملة `test:e2e` ‏3995/3995 في 499 ملفاً؛ سبب فشل انتظار الواجهة غير مثبت ولا يضمن نجاح الإعادة عدم تكراره. نجحت الأنواع و`lint:strict` و`verify:all` ‏351/351 بعد توليد المصفوفة، والبناء و`desktop:compile` و`git diff --check`؛ بقي تحذير حجم الحزم وتُخطي bytecode لغياب Electron. فشل تجهيز الاعتماديات أولاً لتنزيل ترويسات Node، ثم نجح باستخدام الترويسات المحلية؛ أبلغ npm عن 6 ثغرات متوسطة لم تُحلل هنا. لا اختبار Windows/Electron أو تزامن أجهزة حقيقي أو اعتماد مالي أو اعتماد إصدار.

### متابعة — حفظ اليومية والمحتجز التاريخي والإشعارات التالفة
- في طبقة `DesktopStateStorage`، يتحقق استخراج القيود عند تغير دفتر لقطة محفوظة سابقاً من عدم إسقاط القيد القديم أو تغييره أو تكرار معرّفه، حتى إن لم يحدث تعارض مراجعة. يُرفض JSON غير قابل للقراءة عند وجود دفتر معروف. لا يخترع فحصاً لأصل عند أول استيراد، ويسمح بتغيير غير الدفتر مع بقاء دفتر تاريخي تالف كما هو؛ إذا تغير الدفتر التالف يتطلب المراجعة. اختُبر حفظ SQLite حقيقي ورفض إسقاط وتغيير وتكرار ونجاح الإلحاق وإعادة الفتح. هذا حارس في طبقة التطبيق وليس في قاعدة البيانات لكل استدعاء مباشر أو كاتب خارجي؛ قد يكون التغيير وقع في الذاكرة قبل أن يفشل الحفظ، ولا يُعد ذلك تراجعاً ذرياً للحالة الحية. تصميم الإصلاح والمراجعة للسجلات التالفة لم يُنفذ.
- عند مقارنة اللقطات، يحافظ تاريخ المحتجز الآن على حركة ماكينة مرتبطة برقم مستند تحصيل قديم دون لقطة دفع، وعلى ردودها؛ يرفض إضافة الحركة أو إسقاطها أو تغييرها أو تغيير ردها دون تسوية. في احتساب الرصيد والربحية، وجود رد أو إلغاء لحركة تحصيل تاريخية مرتبطة أو تكرار هوية الحركة يحجب الأرقام للمراجعة. غياب الرد أو وجود الحركة لا يثبت التسوية أو صحة التاريخ القديم؛ لا تُخمن أدلة أو تخصصات، ولا يُنشأ عكس للقيد أو تسوية.
- فحص أصل المستخلص وإشعاراته يرفض بعض الأشكال التالفة (قائمة غير قائمة، عناصر أو سطور قيود فارغة، تاريخ أو إجمالي غير صالح) بخطأ مراجعة مالي بدلاً من خطأ لغة؛ رصيد المحتجز يتحقق من شكل الإشعارات قبل استخراج معرفات قيودها. لا يشكل ذلك تدقيقاً شاملاً لجميع الأنواع أو التواريخ أو الإشعارات المستوردة.
- في تدقيق npm: أبلغ `npm audit` عن ست تبعيات تطويرية متوسطة تتصل بسلسلة `electron-builder` و`minimatch`؛ `npm audit --omit=dev` أبلغ عن صفر وفق قاعدة بيانات وقت الفحص. الحل الآلي المقترح يتضمن تغيير إصدار رئيسي، ولم يُطبق أو يُختبر، كما لا تعني النتيجة خلو المنتج من جميع الثغرات.
- **التحقق:** نجحت 153 حالة موجهة في ستة ملفات، و42 في اختبارات المحتجز، واختبارات إضافية للأشكال التالفة والحفظ؛ فشل فحص الأنواع أولاً بسبب تضييق TypeScript صفيفاً إلى `any` وصُحح. نجحت إعادة الأنواع والاختبارات و`lint:strict`، و`verify:all` ‏351/351 بعد توليد المصفوفة، والبناء و`desktop:compile` و`git diff --check`، و`test:e2e` ‏4006/4006 في 500 ملف. حذّر البناء من حجم الحزم وتُخطي Electron bytecode لغياب الثنائي. لم يُختبر Windows أو تزامن أجهزة فعلية أو تُعتمد المعالجة مالياً أو للإصدار.
- **المتبقي:** هذه إصلاحات جزئية لا إنجاز لجميع المراحل أو طلب 15 مرحلة؛ الذرية بين مخزني الفترات والبيانات، ومسار إشعار يعيد المقدمة مع كافة أدلته، وتحصيل وعكس المحتجز الجزئي، والتصحيح الضريبي وإعادة فتح الختامي، وعزل الكيانات والقوائم والتكاملات والاختبارات والاعتمادات الخارجية ما زالت مفتوحة. لا تُرفع الحواجز أو تُصوّر القراءة الجزئية على أنها تسوية كاملة.

### متابعة جزئية — تثبيت أساس الإشعار والموافقة
- في صفحتي المشاريع والمستخلصات تُلتقط بصمة محافظة عند فتح نافذة إشعار المستخلص، تشمل بيانات المشروع واليومية والعميل والمحتجز والتوثيق والخزائن والماكينات والكيانات والفروع والصلاحيات والفترات والإعدادات. بعد إعادة تحميل بيانات المخزن داخل قفل الترحيل، يرفض تغير البصمة، حتى إن كان التغير قبل طلب الموافقة؛ وقد يرفض تغيراً غير متعلق بالمشروع لأن المقارنة متحفظة. يُرفض فتح الإشعار من مراجعة مستخلص تحتفظ بنسخة قديمة.
- يُرفض اعتماد المشرف إذا تغيرت مسودة الإشعار أو أُغلقت أثناء انتظاره، ويُعاد فحصها قبل الترحيل بعد انتظار القفل. تُمنع إعادة الترحيل أثناء الانتظار، وتُغلق النافذة مع تحذير إذا حدث الترحيل محلياً وتعذر تأكيد الحفظ. هذه الحماية تخص مساري الواجهة ولا تمنع الاستدعاء المباشر للمستودع؛ ولا تقفل مخزن الفترات المستقل أو كاتباً خارج القفل أو تضمن تزامن أجهزة حقيقي. لم تُفعّل إعادة مقدمة موجبة أو إشعار بعد تحصيل المحتجز أو فاتورة التوثيق.
- حُسنت مدة ظهور التنبيهات: توقيت رسالة سابقة لا يمسح تحذيراً أحدث، بما في ذلك التحذير من حفظ غير مؤكد. في أول تشغيل شامل لهذه الدفعة نجح 4018/4019 اختباراً وفشل اختبار مرتجع شراء بسبب رسالة توست أصبحت فارغة. تداخل مؤقت قديم مع رسالة أحدث سبب ممكن يثبته اختبار زمني مستقل، لكن سبب تلك الحالة بعينها غير مثبت. نجح الملف الموجه لاحقاً ونجح التشغيل الشامل بعد الإصلاح 4025/4025 في 502 ملف؛ بعده أُضيف اختبار مستقل لإعادة التحميل وثلاث حالات إجمالاً نجحت، واختبار إضافي لتداخل نشر التنبيه مع تعديل ترتيب المؤقت، ونجحت 31 حالة موجهة في أربعة ملفات. لذلك لا يُنسب الاختبار الإضافي ولا تعديل ترتيب المؤقت إلى ذلك التشغيل الشامل.
- نجح `verify:all` ‏351/351، والأنواع و`lint:strict` والبناء و`desktop:compile` مع تحذير حجم الحزم وتخطي bytecode لغياب ثنائي Electron. لم تُستكمل ذرية مخزني البيانات والفترات أو اختبار Windows/Electron والأجهزة الحقيقية أو الاعتماد المالي. المراحل الخمس عشرة تبقى مفتوحة وفق معايير الخطة، وهذه المتابعة ليست إعلان إكمال مرحلة أو جاهزية إصدار.

### متابعة — إيصال إعادة محاولة حفظ SQLite المنفرد
- أضيف ترحيل مخطط سطح المكتب رقم 2 لجدول يحفظ بصمة **آخر** طلب حفظ بمفتاح لكل مخزن. تشمل البصمة المراجعة والحمولة وأحداث التدقيق والقيود المقدمة؛ تحفظ مع اللقطة والأدلة في معاملة واحدة. إعادة الطلب المطابق تعيد المراجعة والوقت الأصليين بلا كتابة، ويُرفض تغيير الأدلة أو إعادة استخدام المفتاح مع مراجعة مختلفة. عند إبطال اللقطة أو حفظها بلا مفتاح يزال إيصالها في المعاملة نفسها. هذا إيصال تكرار محدود وليس سجلاً كاملاً للعمليات أو قيداً يمنع إعادة استعمال مفتاح قديم بعد استبدال آخر إيصال.
- عند ترقية قاعدة قديمة تُنشأ نسخة احتياطية قبل ترحيل المخطط. إذا احتوت آخر لقطة قديمة مفتاحاً بلا إيصال، لا تُخمن الأدلة ولا تؤكد إعادة المحاولة القديمة؛ يُطلب فحص اللقطة والدفتر قبل المتابعة. لا يؤكد الإيصال صحة القيود أو اكتمالها أو مطابقتها للحمولة، ولا يكشف تغيير قاعدة البيانات خارج المسار، ولا يجعل بيانات المشروع والفترات ذريتين. المعاملة الثنائية التجريبية ما زالت غير موصولة؛ حظر الإشعارات والمقدمة الموجبة وتسويات المحتجز والختامي لم يُرفع.
- اختُبر SQLite فعلياً بعد إعادة فتح القاعدة وضياع رد الحفظ، وتغير أدلة الإعادة، وتصادم مراجعة واتصالين، وفشل إدراج أو تحديث الإيصال وحذفه مع التراجع عن اللقطة والقيد والتدقيق والمجموعات، وترقية قاعدة v1 مع فتح نسخة ما قبل الترحيل والتحقق من بياناتها. هذه ليست تجربة تعطل كهرباء فعلي أو Windows/Electron أو تزامن أجهزة متعددة. المقارنة الدقيقة قد ترفض أدلة مكافئة تختلف في ترتيب الخصائص أو القوائم، وتتطلب مراجعة بدلاً من افتراض تطابقها.
- **التحقق:** نجح التشغيل الشامل `test:e2e` ‏4037/4037 في 504 ملفات، والأنواع و`lint:strict`. فشلت أول محاولة `verify:all` في بوابتين قديمتين: الأولى أعادت طلب الحفظ دون الأدلة الأصلية والثانية افترضت مخطط 1 وترحيلاً افتراضياً برقم 2؛ عُدلت البوابتان لاختبار الأدلة نفسها والترحيل الافتراضي التالي، ونجح كل منهما ثم `verify:all` ‏351/351. نجح البناء و`desktop:compile` و`git diff --check`؛ بقي تحذير حجم الحزم وتخطي bytecode لغياب ثنائي Electron. لم تُستكمل المراحل ولا يوجد اعتماد مالي أو جاهزية إصدار.

### متابعة جزئية — مطابقة أساس قيد إقفال السنة
- قبل الاستعادة الآلية للحالة أو قبول قيد سابق أو عكسه، يُعاد بناء أسطر الإقفال من حركة الفترة السابقة للقيد حسب ترتيب اليومية والفرع، مع استبعاد آلية الإقفال والعكس، ومقارنتها بإجمالي كل حساب واتجاهه؛ لا يُقبل قيد متوازن وحده دليلاً على إقفال حركة مختلفة أو مفقودة. تُقبل القيود التذكارية الصفرية الصريحة، ويُحجب الأساس التالف أو قيد إقفال من سنة أخرى داخل الفترة للمراجعة. إسناد القديم للرئيسي يتبع معرف الفرع الرئيسي الممرر.

### متابعة محرر الخطابات — تحديد مواضع التنبيهات
- تعرض لوحة التخطيط رقم الصفحة وأسماء العناصر المتداخلة أو العنصر المتجاوز لحدود الصفحة. اختيار الاسم يحدد العنصر في أدوات الموضع ويركز عليه في المعاينة لتحريكه بالسحب أو الأسهم؛ لا ينقله أو يعدّل التخطيط تلقائياً. يعرض أول 20 تنبيهاً وعدد الباقي، ويُعاد فحص جميع الصفحات عند التصدير مع بقاء تأكيد المتابعة عند وجود تنبيه.
- الفحص يعتمد مستطيلات العناصر الظاهرة في معاينة المتصفح، ويستثني الخطوط الزخرفية؛ ليس ضماناً للتوافق مع Word أو كل الخطوط والطابعات أو اكتشاف كل قص محتمل. لا يحل مشكلة التداخل الافتراضي لبعض بيانات المستلم، ولا يضيف تدفقاً تلقائياً للنص. المراحل المالية المفتوحة بقيودها المذكورة أعلاه لم تُنجز أو تُعتمد.
- الاختبارات الموجهة 37/37 تشمل كشف التداخل والخروج، واختيار العنصر من تنبيه صفحة ثانية، وزوال التنبيه عند تغير القياس ورفض متابعة PDF عند إلغاء التأكيد. في Chromium فُحص تداخل التاريخ والموضوع واختياره وإزالة التداخل، ثم اكتشاف خروج التاريخ من الصفحة دون أخطاء واجهة. أول محاولة للمتصفح فشلت لعدم ضبط مسار مكتبات NSS، ونجحت بعد ضبطه. نجحت الأنواع وأنواع الاختبارات وlint والبناء وdiff مع تحذير حجم الحزم. لم يُجر تشغيل شامل جديد أو اختبار بصري في Word أو طباعة فعلية.

### ستة قوالب للخطابات وخلفيات رسمية قابلة للتخصيص
- أُضيفت تصاميم مؤسسية وتراثية وهندسية إلى القوالب الكلاسيكية والحديثة والبسيطة، فأصبحت ستة بتوزيعات مختلفة؛ تضم التصميمات الجديدة خلفيات زخرفية، وهناك خمس خلفيات جاهزة يمكن اختيار أي منها أو إخفاؤها. لا تُغيَّر الخطابات المحفوظة القديمة التي لا تتضمن إعداد خلفية.
- زر «التحكم في القوالب» في القسم يفتح محرر خطاب مع لوحة التحكم، والزر داخل المحرر يفتحها أو يغلقها. يمكن ضبط شفافية الخلفية من صفر إلى مئة (مئة تخفيها)، أو رفع PNG/JPEG حتى 1 ميغابايت وأبعاد 4096 بكسل. تُمد الخلفية على كل الصفحات وتحفظ مع الخطاب. يمكن حفظ حتى عشرة تصاميم مسماة في نطاق الفرع، وحذفها أو تطبيقها على خطاب آخر بعد التأكيد؛ تحفظ المواضع وتوزيع الصفحات والخلفية وترتيب مواضع الفقرات، ولا تنسخ النصوص أو بيانات العميل أو تنسيقات الخط. حذف قالب لا يغير الخطابات التي سبق تطبيقه عليها. تحرس عمليات الحفظ الصلاحية وقفل الحفظ وتعارض الدمج، دون ادعاء اختبار أجهزة متعددة.
- الخلفية تظهر في PDF والطباعة وWord؛ يصدر Word صورة شفافة خلف النص القابل للتحرير لكل مقطع. جُرب Chromium: رفع صورة فعلية، تغيير الشفافية، حفظ القالب والخطاب وإعادة التحميل، وPDF بصفحة وصفحتين مع فحص صورة الصفحة الثانية، وطباعة المتصفح إلى PDF بخلفية. فُحص DOCX مولد حقيقي: محتوى قابل للتحرير، رأس لكل صفحة، صورة خلف النص ومعامل شفافية مطبق في الصورة. لم يُختبر العرض بصرياً في Microsoft Word أو LibreOffice أو طابعة فعلية، وقد تختلف إطارات Word وإعدادات طباعة الخلفية. تحذيرات التداخل والقص لا تضمن خلو التخطيط من الأخطاء، وقد تحتاج حقول المستلم الإضافية للتحريك يدوياً.
- نجحت 43 حالة موجهة، و`test:e2e` ‏4092/4092 في 511 ملفاً، وأنواع التطبيق والاختبارات وlint والبناء و`git diff --check`؛ البناء حذر من حجم الحزم. فشل `verify:all` أولاً في بوابتي مصفوفة المحرك القديمة والمقارنات الحرفية بسبب MIME صورة وحالة تحميل خطوط DOM؛ أُعيد توليد المصفوفة وحددت استثناءات الفحص لهذين الموضعين، ثم نجح `verify:all` ‏351/351. لا يعني ذلك اكتمال المراحل المالية المفتوحة أو اعتمادها أو اختبار Windows/Electron حقيقياً.

### تحديث الخطابات — ترويسة وتوقيع وقوالب إضافية
- أعيد توزيع بيانات المنشأة والمستلم في الترويسة، مع تذييل أفقي، وعناصر قابلة للسحب والتنسيق المستقل؛ القوالب 11 بينها خمسة جديدة. الخطابات المحفوظة القديمة تحافظ على توزيعها، وزر إعادة الترتيب يحتاج تأكيداً ويعيد المواضع والصفحات.
- يمكن رفع PNG/JPEG للتوقيع والختم أو رسم توقيع حر، مع تحريك الصورتين وتغيير حجمهما وحفظهما في الخطاب وتصديرهما. الصور ليست توقيعاً إلكترونياً موثقاً. قالب افتراضي جاهز أو مخصص بنطاق الفرع للخطابات الجديدة فقط، مع صلاحية الخطابات وقفل وحارس دمج، والعودة للكلاسيكي عند حذف التصميم الافتراضي.
- جرب Chromium أحد عشر قالباً ببيانات منشأة ومستلم كاملة دون تنبيهات للتداخل في الحالة التجريبية، والرسم والرفع والتصدير PDF وDOCX والحفظ وإعادة التحميل وتطبيق الافتراضي. قد تلتف البيانات الطويلة، ويجب مراجعة تحذيرات المعاينة وتحريك الحقول؛ لا يعاد تدفقها تلقائياً. لم يختبر Word/LibreOffice أو الطباعة الفعلية بصرياً ولا تزامن أجهزة مستقلة.
- فحوص التحديث: اختبارات الخطابات الموجهة 46/46، والأنواع وأنواع الاختبارات وlint والبناء و`git diff --check` ناجحة. فشلت `verify:all` أولاً لقدم مصفوفة المحرك، ثم أُعيد توليدها ونجحت البوابة منفردة وإعادة التحقق كاملة 351/351. لم يُعد تشغيل الشامل بعد هذا التحديث؛ نتيجته السابقة 4092/4092 تخص الحالة السابقة. البناء يحذر من حجم الحزم.

### تصحيح مواضع الخطاب والتذييل
- إصدار تخطيط جديد للقوالب الجاهزة: اسم الجهة وبياناتها المسجلة مقابل بيانات المنشأة فوق الخط، وأسفل الخط الموضوع يميناً وتحته «إلى السادة» ثم التحية، والرقم والتاريخ يساراً بحجم صغير متتابعين. باقي العناصر قابلة للتحريك والتنسيق.
- تذييل بيانات المنشأة كتلة ثابتة في كل صفحة، مرتبة في سطور للعنوان والاتصال والسجل والرقم الضريبي، لا تُحرّك من الشاشة أو إحداثيات القالب. يلتف النص الطويل ويُحذّر عند خروجه؛ يحتاج المستخدم لاختصار البيانات الطويلة جداً. الصياغة شكل عملي وليست ادعاء اعتماد رسمي أو قانوني.
- حفاظاً على المستندات، التخطيطات والقوالب المخصصة المحفوظة سابقاً لا تتغير تلقائياً وقد يبقى تذييلها القديم قابلاً للتحريك؛ لتنفيذ التصحيح فيها اختر «إعادة ترتيب عناصر القالب» (أو اختر قالباً للعرض القديم)، وراجع أثر إعادة ضبط المواضع والصفحات ثم احفظ. التذييل الجديد مكرر في PDF وWord؛ لم يُفحص Word بصرياً في برنامج مكتبي أو طابعة فعلية.
- فحص Chromium بيانات كاملة في 11 قالباً ولم تظهر تنبيهات في الحالة المختبرة، مع تصدير PDF وDOCX. نتائج الاختبارات والبناء توثق بعد انتهائها؛ ليست هذه مراجعة للمراحل المالية التي ما زالت مفتوحة.
- التحقق: اختبارات الخطابات الموجهة 49/49، والأنواع وأنواع الاختبارات وlint والبناء و`git diff --check` ناجحة، و`verify:all` ‏351/351. البناء يحذر من حجم الحزم. لم يُعد تشغيل الشامل الكامل في هذا التحديث.

### تقارب بيانات الترويسة
- قُلصت المسافات بين بيانات المنشأة والجهة، ووضعت بيانات المنشأة في عمود واحد بجوار الشعار، ورُفع الخط الفاصل وما تحته في التخطيطات الجديدة لتقليل الحيز الرأسي. لا تزال الحقول قابلة للتحريك والتنسيق؛ قد تستلزم بيانات طويلة توسيع الحقل أو تحريكه مع مراجعة تحذيرات التداخل.
- الخطابات والقوالب المحفوظة لا تتغير بصمت. في تخطيط الإصدار 2 أو 3، زر «تقريب بيانات الترويسة» يعيد مواضع حقول بيانات الطرفين فقط مع المحافظة على صفحاتها وتكرارها وبقية العناصر؛ تُحفظ النتيجة عند حفظ الخطاب ويمكن حفظ تصميم جديد. التخطيط الأقدم يحتاج إعادة ترتيب القالب بعد التأكيد.
- جُربت الترويسة كاملة مع الشعار في Chromium للقوالب الأحد عشر دون تحذيرات في المثال المختبر. جُرب PDF وDOCX قبل ترقيم الإصدار الجديد؛ وفي التجربة الأخيرة نجح PDF لكن انتظار زر Word انتهى بمهلة أثناء إعادة تحميل الصفحة، واختبار Word البنيوي ناجح. اختبارات الخطابات الموجهة 51/51. لا يثبت ذلك توافق التفاف Word المرئي أو الطباعة الفعلية، ولا يغير حالة المراحل المالية المفتوحة.
- إعادة تجربة Word وحده لم تبدأ لأن Chromium نفسه توقف بإشارة SIGSEGV؛ لا يُستنتج من ذلك سبب فشل التطبيق أو نجاح التصدير الأخير. فحص DOCX البنيوي بقي ناجحاً. اكتمل فحص الأنواع وأنواع الاختبارات وlint والبناء و`git diff --check`، و`verify:all` ‏351/351؛ البناء يحذر من حجم الحزم ولم يُعد تشغيل الشامل الكامل.

### مسافات الترويسة بتحكم المستخدم
- أضيف إصدار رابع للقالب يباعد عمودي بيانات المنشأة والجهة ويقرب السطور والخط الفاصل، دون تغيير تخطيطات الخطابات والقوالب المحفوظة سابقاً. التحكم الجديد متاح أيضاً لإصداري التخطيط 2 و3 دون إعادة ترتيب الخطاب كله، مع الاحتفاظ بالتذييل الثابت.
- لوحة «التحكم في مسافات الترويسة» تضبط المسافة بين العمودين (بتعديل عرض حقول الجهة)، وتباعد سطور كل جهة، والمسافة بين آخر عنصر ظاهر والخط الفاصل بقياس المعاينة. تغيير السطور يرتب الحقول الظاهرة قبل الفارغة؛ زر الرص يتيح ذلك صراحةً بعد تغيير البيانات. تبقى صفحات العناصر وتكرارها، ولا تنتقل بقية العناصر تلقائياً؛ قد يتسبب التفاف النص أو تحريك الخط في تداخل ويُحذر منه في المعاينة. يمكن حفظ التصميم وإعادة استخدامه.
- جرب Chromium القوالب الأحد عشر مع بيانات وشعار دون تنبيهات في المثال الافتراضي، وأثبت التحكم في المسافات الأربعة، وظهر تحذير مقصود حين تداخل الخط مع الموضوع والرقم. اختبارات الخطابات الموجهة 55/55. Word قابل للتعديل لكن لا يوجد إثبات بصري للتطابق في Word/LibreOffice؛ لا تكتمل المراحل المالية بهذا العمل.
- التحقق: اختبارات الخطابات الموجهة 55/55، والأنواع وأنواع الاختبارات وlint والبناء و`git diff --check` ناجحة، و`verify:all` ‏351/351. فشل فحص الأنواع الأول بسبب استيراد غير مستخدم، حُذف الاستيراد وأعيد الفحص والبناء بنجاح. البناء يحذر من حجم الحزم؛ لم يُعد تشغيل الاختبارات الشاملة أو اختبار الطباعة الفعلية.


### تثبيت تصميم الخطاب وإصلاح التذييل في الطباعة
- أضيف زر «تثبيت تصميم هذا الخطاب افتراضياً» ضمن التحكم في القوالب والخلفية: يحفظ نسخة فرعية من المواضع والخلفية وتنسيق الخطوط وخانات الفقرات دون نصوصها أو بيانات المستلم أو صور التوقيع والختم، ويطبقها على الخطابات الجديدة فقط. يعاد تثبيته لتحديثه، ولا يغير التصاميم أو الخطابات السابقة تلقائياً. لا يمكن استنتاج مواضع تعديل المستخدم الدقيقة من الصورة وحدها؛ يجب تثبيت الخطاب المطلوب من جهازه.
- أصلحت قواعد HTML المرسل للطباعة لتموضع وتنسيق التذييل وخطه السفلي، دون تغيير طباعة الخطاب القديم. في تجربة Chromium لطباعة خطاب من صفحتين إلى PDF ظهر التذييل وخطه أسفل الصفحة ضمن الورقة في الصفحتين، دون أخطاء صفحة؛ ليست تجربة على طابعة فعلية.
- اختبارات الخطابات الموجهة 58/58 ناجحة، وتغطي طباعة الصفحتين والتوافق القديم وتثبيت التنسيق وعزل الفروع ورفض تعارض التعديل. Word لم يُفحص بصرياً، والمراحل المالية لا تزال مفتوحة وغير معتمدة.
- التحقق النهائي: الأنواع وأنواع الاختبارات وlint والبناء و`git diff --check` ناجحة، و`verify:all` ‏351/351 بعد إعادة توليد مصفوفة المحرك التي تغيرت أرقام أسطرها. البناء يحذر من حجم الحزم؛ لم يُعد تشغيل مجموعة الاختبارات الشاملة الكاملة لهذا التحديث.

### إظهار عناصر الترويسة والقالب الكامل
- في التخطيط الجديد يمكن إظهار وإخفاء الشعار واسم المنشأة وبياناتها واسم الجهة وحقولها وخط الترويسة كلٌ على حدة، دون حذف البيانات أو تغيير التذييل الثابت. اسم المنشأة مخفي افتراضياً في التصميم الجاهز الجديد؛ تبقى نسخته في بيانات الخطاب ويمكن إظهاره، ولا يُفرض إدخال الاسم عند الحفظ. الخطابات والقوالب القديمة المحفوظة لا تتحول تلقائياً، وللعرض القديم يجب اختيار قالب للتحكم بالترويسة.
- حفظ القالب المسمى والتحديث من الخطاب يحفظان جميع إحداثيات العناصر وصفحاتها وتكرارها والخلفية وشفافيتها وإظهار الترويسة وتنسيقات الحقول والفقرات. يمكن اختيار القالب الافتراضي للفرع؛ لتغيير قالب محفوظ استخدم «تحديث من الخطاب»، الذي يرفض تعارض النسخة ويؤثر على الخطابات الجديدة فقط. القوالب القديمة التي لم تحفظ التنسيقات سابقاً لا يمكن استعادة تنسيقات لم تخزن؛ يمكن تطبيقها وضبطها وتحديثها.
- خيار تضمين نصوص الفقرات والتحية والختام والموقّع وصور التوقيع والختم محدد افتراضياً، ويمكن إلغاؤه. بيانات العميل والموضوع والرقم والتاريخ لا تُنسخ؛ تُستخدم بيانات المنشأة الحالية في الخطابات الجديدة. حفظ الصور يعني تكرارها في كل خطاب جديد، وهي ليست توقيعاً رقمياً معتمداً. أزيلت صور اختيار القالب المكررة للقائمة وزر الحفظ الافتراضي المختصر المكرر لمسار حفظ القالب واختياره.
- طبقت حالة الظهور على المعاينة والطباعة وPDF وWord، وأصلحت مسافة أسطر Word لتقارب إعداد المعاينة. فحص Chromium حفظ القالب واختياره وإعادة تحميله، مع نص وتنظيم وإخفاء وخلفية، والتحقق من HTML الطباعة وتصدير DOCX بنيوياً؛ لا يثبت ذلك المطابقة المرئية في Word أو اختبار طابعة فعلية. النصوص الطويلة تحتاج مراجعة التنبيهات.
- اختبارات الخطابات الموجهة 63/63، والأنواع وأنواع الاختبارات وlint والبناء وdiff ناجحة، وverify:all ‏351/351 بعد إعادة توليد مصفوفة المحرك. البناء يحذر من حجم الحزم؛ لم تُعد الاختبارات الشاملة الكاملة، والمراحل المالية لا تزال مفتوحة وغير معتمدة.

### مراجعة متابعة الخطابات — نسب الصور في Word
- عولج اختلاف تصدير الشعار في تخطيط Word: كان يتمدد إلى أبعاد الصندوق كاملاً، بينما المعاينة تحافظ على النسب؛ أصبح يحتفظ بنسبة الصورة، ويُوسّط عمودياً ضمن الصندوق عند وجود فراغ، وكذلك صور التوقيع والختم. الخطاب القديم دون تخطيط لم يتغير. يفحص التصدير أبعاد الشعار المرئي، ولا يحمل الشعار المخفي.
- اختبار بنيوي يتحقق من نسبة الصورة وموضعها ومن إخفاء الشعار. تجربة Chromium صدّرت خطاباً من صفحتين إلى PDF وDOCX وتحققت من عدد صفحاته وHTML الطباعة وتذييليه ونسبة شعار 2:1 في DOCX؛ لم يُفحص عرض الملف في Word أو LibreOffice أو على طابعة فعلية، ولا يُضمن تطابق التفاف النص في كل خط أو برنامج.

### متابعة — مراجعة أساس الاستعادة الملفية بعد إغلاق SQLite
- يفحص مسار استعادة الملف نسخة الأمان المأخوذة من قاعدة التشغيل بعد الإغلاق، ويعيد مقارنة أدلة اليومية والسنوات والأرقام وسجلات المشروع والخطابات مع ملف المرحلة قبل الاستبدال. يرفض نسخ الأمان غير السليمة أو الأدلة التي ظهرت بعد الفحص الأول، ويبقي قاعدة التشغيل ونسخة الأمان دون استبدال عند الفشل.

- اختبارات قواعد SQLite فعلية تغطي قيداً ظهر بين الفحص الأول والإغلاق، وتغيير المرحلة أو قاعدة التشغيل أثناء إعداد النسخة، وفشل فحص الأمان، وفقد ملف المرحلة، والنجاح ورفض WAL. الاختبارات الموجهة 113/113، وأنواع الاختبارات والبناء وlint وترجمة سطح المكتب ناجحة؛ إصدار bytecode لم يُبن لعدم وجود ثنائي Electron في البيئة. نجحت أيضاً `verify:all` ‏369/369 (349 بوابة و20 رحلة)، ولم تُعد مجموعة `test:e2e` الكاملة لهذا التعديل.

- التحقق المحلي: أنواع التطبيق والاختبارات و`lint:strict` والبناء نجحت، واختبارات الإقفال والتقارير والتشغيل الموجهة 112/112 في 18 ملفاً؛ بقي تحذير حجم الحزم. أُعيد توليد مصفوفة المحرك ونجحت بوابتها 43/43 و`verify:all` ‏369/369. لم يُعد `test:e2e` كاملاً بعد هذه الدفعة، ولا اختُبر Windows أو جهاز العميل أو GitHub أو تعدد الأجهزة، ولم يُنشر إصدار.

### متابعة — خمس خطوات جزئية لإظهار حالة السنة للمراجعة
1. إضافة مؤشر قراءة فقط يقارن حالة السنة بقيود الإقفال الظاهرة، وينبّه إلى التعارض أو تعدد الإقفالات النشطة أو غيابها عند الإقفال.
2. تدقيق سلامة قيد الإقفال الظاهر من حيث الهوية والتاريخ والأسطر والمبالغ، والتنبيه للحالات المكررة أو الحالة غير المعروفة أو اختلاف الفرع الصريح.
3. فحص روابط العكس الظاهرة وترتيبها وتطابق أسطرها وأبعادها وتفرد المطالبات، دون اعتبار الرابط المنفرد دليلاً كافياً.
4. عرض تنبيه عام في إعدادات السنة دون تفاصيل قيود أو فروع أخرى ودون تعديل حالة السنة أو اليومية، وتوضيح أن غياب التنبيه لا يثبت سلامة الإقفال؛ تُفهرس البيانات وتُحفظ نتيجة الحساب بين التحديثات غير المتعلقة بها.

- وحّد حساب تاريخ نهاية الضمان التقويمي بين المراجعة والجرس: تحقق من التاريخ الفعلي والمدة الصحيحة 0–1200 شهر، وآخر الشهر وتجاوز السنة، وحجب السنوات 0–99 التي يعيد JavaScript تفسيرها تاريخياً. احتُفظ بمدة الصفر عند فتح محرر المشروع وحفظ تعديل آخر بدلاً من إسقاطها. التاريخ المحسوب ليس إثباتاً للتسليم أو للاستحقاق وفق العقد.
- جرس التنبيهات يتحقق من رصيد المحتجز لكل مشروع ظاهر، حتى عند غياب تاريخ التسليم: يميز خطأ الأدلة المالية عن الحاجة لمراجعة التاريخ عند وجود رصيد موجب، ويعزل خطأ مشروع عن تنبيهات السليم. نص التنبيه يطلب مراجعة العقد والتسليم والاستحقاق بدلاً من الجزم باستحقاق المحتجز. المتبقي الذي يفحصه الجرس يعتمد حراسات الدفتر الموجودة ولا يثبت كل الأدلة أو اكتمال البيانات؛ القراءة قد تكون مكلفة مع كثرة المشاريع والقيود ولم تُقَس على قاعدة عميل كبيرة.
- نجحت 83/83 حالة موجهة في 11 ملفاً، ثم 35/35 بعد إعادة ترتيب دوال التنبيه؛ و`test:e2e` ‏4595/4595 في 563 ملفاً قبل إعادة ترتيب الدوال المكافئة، ولم يُعد الشامل بعد ذلك. نجحت الأنواع للتطبيق والاختبارات و`lint:strict` والبناء (مع تحذير حجم الحزمة)، ومصفوفة المحرك 43/43 و`verify:all` ‏369/369 بعد إعادة فحص الشجرة. فشل التشغيل الشامل الأول في حالتين بسبب تغيير مصدر واختبار أثناء تشغيله، ثم نجح التشغيل المعاد؛ أوقف تشغيل متوازٍ آخر بعد نفاد الذاكرة وشُغلت الفحوص الثقيلة تباعاً.
- **الحدود:** لا يتيح هذا إقفالاً شاملاً أو إعادة فتح الختامي، ولا يثبت سداد ذمم العملاء أو مقاولي الباطن أو العهدة أو تكاليف المشروع، ولا يغطي السجلات المخفية خارج نطاق الفرع أو جميع الأدلة المشتركة. الحواجز المالية باقية ولم يُختبر تزامن أجهزة أو Windows أو جهاز العميل أو GitHub على هذا الرأس؛ لا إغلاق مرحلة أو اعتماد مالي أو إصدار.

### متابعة — حفظ حالة إقفال المشروع المرتبط بتحصيل المحتجز (جزئية)
- تبيّن باختبار قبل الإصلاح أن حارس التاريخ كان يحفظ سجل التحصيل وأدلة تخصيصه لكنه يسمح للقطة واردة بإعادة المشروع المحلي المقفل إلى نشط مع إبقاء سجل التحصيل. أصبح يرفض إسقاط المشروع أو تكراره أو تغيير حالته أو توقيت إقفاله أو فرعه حين كان محلياً مقفلاً وله تحصيل محفوظ؛ ويسمح بالتعديل المستقل وبانتقال التحصيل الطبيعي من الحالة النشطة. يُستعمل الحارس في الاستعادة والسحب واستعادة لقطة التعارض ودمج التخزين، ولا يُستنتج إقفال مشروع تاريخي نشط من سجل تحصيله وحده.
- مسار `updateProject` القديم يقبل وقت التنفيذ حقولاً خارج نوعه، ومنها معرّف المشروع والفرع وتاريخ الإقفال. فُرضت قائمة حقول التعديل نفسها التي يستعملها التعديل الكامل، مع بقاء منع تعديل سجل التواصل التاريخي. لا يمنح ذلك صلاحيات إضافية ولا يحمي كاتباً يتجاوز إجراءات المستودع.
- اختبارات جديدة تنفذ تحصيل المحتجز ثم تقارن اللقطات، وترفض السحب السحابي المحاكى دون تغيير مراجعة السحابة، وتفحص ملفي SQLite فعليين دون إغلاق القاعدة الحالية، وتفحص حقول التعديل والقبول المشروع. لم يُختبر تزامن أجهزة حقيقي أو استعادة على Windows. الحارس يحمي ما هو موجود محلياً ولا يثبت صحة كل الوارد أو صحة الاستحقاق؛ لا يعالج مشروعاً محلياً مفقوداً أو نشطاً رغم وجود تحصيل قديم، ولا يمنع كاتباً خارج الآلية.
- **نطاق مفتوح:** مراجعة مسارات جدول الكميات وأوامر التغيير والباطن بعد حالة المكتمل ما زالت مطلوبة؛ بعض العمليات القديمة لا تفحص حالة المشروع. لم تُحجب هنا إذ قد تتطلب معالجة التزامات سابقة وتصميماً واعتماداً قبل فرض سياسة إقفال شاملة. لم تُفعّل إعادة فتح أو تحصيل جزئي أو عكس أو رد مقدمة، ولا يثبت تحصيل المحتجز التسليم أو التسوية الكاملة.
- التحقق المحلي: 153/153 اختباراً موجهاً في 10 ملفات؛ أنواع التطبيق والاختبارات و`lint:strict` والبناء ناجحة مع تحذير حجم الحزم؛ المصفوفة 43/43 و`verify:all` ‏369/369. لم يُعد `test:e2e` الشامل في هذه الجولة؛ آخر نتيجة سابقة 4595/4595 قبل إعادة هيكلة التنبيه. لم يُنشر إصدار أو يُمنح اعتماد مالي، والمراحل الأصلية باقية مفتوحة.

### متابعة — صون المستخلص الختامي عند التعديل والاستعادة (جزئية)
- أثبتت اختبارات قبل الإصلاح أن تعديل مستخلص ختامي مع `isFinal: false` أو بإغفال الحقل كان يسقط علامته ويسمح بتخفيض المبلغ خارج شرط الختامي، كما أمكن تحويل مستخلص سابق إلى ختامي مع وجود ختامي آخر. يرفض المستودع التحويل الصريح إلى جزئي، ويحافظ على الختامي عند الإغفال، ويطبق شرط مساواة العقد؛ كما يرفض جعل مستخلص ختامياً إذا وُجد ختامي آخر أو مستخلص أحدث. يظل تعديل الختامي نفسه ممكناً وفق حراسات التعديل القائمة وبشرط بقاء طبيعته، ولا يمثل إعادة فتحه.
- عطّل محررا تفاصيل المشروع وقائمة المستخلصات إزالة علامة الختامي، وعطلت تفاصيل المشروع التعبئة السريعة التي تغيرها، مع توضيح السبب. اختبارا واجهة يحاكيان التحرير من المسارين؛ لا يُعتمد تعطيل الواجهة بدلاً من حراسة المستودع.
- حارس تاريخ المشروع يرفض إسقاط المستخلص المحلي الختامي أو نقل ارتباطه بالمشروع أو الفرع أو إسقاط علامته في اللقطة الواردة، ويرفض إضافة ختامي آخر أو مستخلص جديد ذي معرف أعلى إلى المشروع المحمي. اختُبرت المقارنة والدمج والسحب المحاكى وفحص استعادة SQLite الفعلي، مع بقاء القاعدة الأصلية مفتوحة عند الرفض. يُقبل التعديل الفعلي الذي يحتفظ بالطبيعة، ولا يثبت الحارس صحة القيد أو كل حقول المستخلص أو كل السجلات الواردة. المعرف قرينة ترتيب تحفظية، وليس دليلاً قاطعاً على زمن السجل؛ التاريخ الملتبس قد يتطلب مراجعة مستقلة. البيانات التي لا تحتوي الختامي محلياً أو الكتّاب خارج مسارات المقارنة ليست مغطاة بهذه الحراسة.
- التحقق: الموجهة 187/187 في 12 ملفاً قبل إضافة تأكيد قبول التعديل الفعلي، وقد شمله الاختبار الشامل اللاحق. أنواع التطبيق والاختبارات و`lint:strict` والبناء ناجحة بتحذير حجم الحزمة؛ `test:e2e` نجح 4609/4609 في 565 ملفاً، مع تحذيرات React وjsdom ومهلة إنهاء عامل Vitest وخروج ناجح. المصفوفة 43/43 و`verify:all` ‏369/369 ناجحة. لم يُختبر Windows أو التزامن الحقيقي أو جهاز العميل، ولم يُصدر اعتماد أو نسخة؛ لا تحصيل جزئي أو رد مقدمة أو إعادة فتح الختامي، ولا تعدّ هذه المتابعة إقفالاً لأي مرحلة أصلية.

### متابعة — تباعد واصطفاف حقول عرض السعر (إكمال محلي للبند الإضافي)
- كان إصلاح التباعد السابق خاصاً بمحرر العرض، لكن قياس Chromium كشف أن الحد الأدنى العام لارتفاع بعض التسميات بقي أكبر من تسمية عنوان الأعمال ذات الأيقونة، فظهرت مدخلات الصف نفسه غير مصطفة عند 900 بكسل وما فوق. أزيل الحد الأدنى للتسميات ضمن محرر العرض فقط، مع الإبقاء على المسافة والصف المرن؛ لا تغير لقواعد فاتورة البيع المشتركة. أضيف اسم وصول لحقل تاريخ «ساري حتى».
- أضيف اختبار Chromium قابل لإعادة التشغيل يحاكي المستند الحقيقي، ويقيس تباعد كل تسمية وعدم قصها واحتواء المدخلات واصطفاف الحقول وعدم تداخلها في العرض والمناقصة عند 360 و660 و900 و1280 و1920 بكسل، ويفحص حجم حقلي العميل وعمل اختيار العميل وتغيير الصلاحية وإدخال البنود والضريبة. يتحقق كذلك من فتح عرض محفوظ ومن بقاء هندسة ترويسة فاتورة البيع وإجراءات نوع الطرف والتاريخ والملاحظات. بيئة الاختبار تعزل التخزين في الذاكرة وترفض جسر سطح المكتب. الاختبار البنيوي لاصطفاف الصف فشل قبل الإصلاح ونجح بعده.
- نجح اختبار Chromium بعد ضبط مسار المكتبات `LD_LIBRARY_PATH=/tmp/al2023/lib` والثنائي المتاح؛ أول محاولة فشلت لغياب مكتبات NSS من مسار التحميل. نجحت اختبارات العروض والفواتير الموجهة 37/37 في 3 ملفات، وأنواع التطبيق والاختبارات و`lint:strict` والبناء بتحذير حجم الحزم، و`verify:all` ‏369/369 قبل إضافة حالة تحرير العرض إلى اختبار المتصفح المستقل، الذي أعيد ونجح. لم يُعد `test:e2e` الشامل لهذه الإضافة؛ نتيجته السابقة 4609/4609 في 565 ملفاً.
- **الحدود:** اختبار Chromium headless بمقاسات نافذة ليس اختباراً على جهاز العميل أو Windows/Electron أو متصفحات أخرى أو قارئ شاشة فعلي، ولا يثبت جميع وظائف الفاتورة؛ تبقى تلك الاختبارات والاعتمادات ضمن المرحلة 10. لم تُقفل المراحل المالية أو تُغيّر حواجزها أو يُنشر إصدار.

### متابعة — حفظ تعديل المستخلص وقيد عكسه (جزئية)
- كشف اختبار مسار فعلي في SQLite أن عكس تعديل المستخلص كان يحمل معرف المستخلص في `sourceId`، بينما تشترط حراسة اليومية وحفظ SQLite معرف القيد الأصلي. عند اختلاف الرقمين لم تكن اللقطة قابلة للحفظ كعكس صحيح. صار العكس الجديد يحمل معرف القيد الأصلي، ويبقى ارتباط المستخلص على القيد البديل وفي `editReversalEntryId`؛ لم تُخفف حراسات اليومية ولم تُغيّر القيود التاريخية.
- عند تفعيل فرع بعد إنشاء قيد مستخلص قديم بلا فرع، ينسب الكاتب العام العكس الجديد إلى الفرع النشط، لكن حارس اليومية يشترط تطابق فرع العكس والأصل. بدلاً من حفظ غير ممكن أو تخمين نسبة تاريخية، يرفض مسار التعديل هذه الحالة قبل تغيير الحالة ويطلب مراجعة النسبة. لا يعالج ذلك كل مسارات عكس القيود القديمة.
- الاختبار يصدر ختامياً بعد قيد مستقل، ثم يعدله مرتين ويحفظ كل لقطة عبر `DesktopStateStorage` وSQLite فعلي، ويفتح القاعدة مجدداً، مع فرع وبدونه. يفحص رفض مصدر عكس خاطئ وعدم تغيير اللقطة، والحفاظ على دليل عكس قديم كما هو، ورفض تعديل الأصل غير المنسوب بعد تفعيل الفرع. لا يثبت إعادة فتح قاعدة العميل أو استعادة ملف حقيقي أو مزامنة أجهزة؛ ولا يصلح تلقائياً عكساً تاريخياً أُنشئ بالمصدر القديم أو يثبت صحته. قد تتطلب هذه السجلات مراجعة مستقلة.
- **فجوة مفتوحة إضافية:** حارس هوية الختامي لا يضمن ثبات كل بيانات المستخلص المرتبطة بقيده؛ في فحص استكشافي قَبِل تغيير رقم مستخلص ختامي وارد مع إبقاء مرجع قيده. لا يُعد ذلك إثباتاً لصحة اللقطة، ويلزم تصميم واختبارات تربط الأساس المالي والتعديلات بعكس صحيح وقيد بديل مع مراعاة التاريخ القديم قبل تشديد حراس الاستعادة والدمج. لم تُفعّل إعادة الفتح أو التحصيل الجزئي أو رد المقدمة أو أي تسوية جديدة.
- التحقق: أنواع التطبيق والاختبارات و`lint:strict` والبناء نجحت، وكذلك الاختبارات الموجهة؛ فشل أول `verify:all` في بوابة واحدة من 369 لأن مصفوفة المحرك لم تكن محدثة بعد تعديل الكود، ثم أُعيد توليدها ونجحت بوابتها 43/43. ثم نجحت إعادة `verify:all` ‏369/369 بعد توليد المصفوفة. لم يُعد الشامل `test:e2e` في هذه الجولة ولم يُختبر Windows أو جهاز العميل أو يُمنح اعتماد مالي؛ لا تُقفل مرحلة بهذا العمل.

### متابعة — صون أساس الختامي المحلي عند ثبات مرجع القيد (جزئية)
- اختبرنا الفجوة السابقة: قَبِل حارس تاريخ المشروع تغيير رقم المستخلص الختامي دون تغيير القيد. صار يرفض تغيير رقم الختامي المحلي أو وقت إنشائه، ويرفض تغيير تاريخ المستند أو طريقة السداد أو الإجماليات أو بنود الحصر أو استرداد المقدمة وتخصيصه مع الإبقاء على مرجع القيد أو غياب مرجع صالح. يسمح بالتغيير الوصفي المستقل، وبالمقارنة مع تعديل فعلي يغيّر القيد ويحافظ على الهوية؛ لا يُختلق وقت إنشاء أو دليل قديم. قد تحتاج اللقطات التاريخية المخالفة للمراجعة بدلاً من الاستعادة الصامتة.
- اختبارات المقارنة والدمج تغطي كل حقل محمي، والمعرف غير الموجود، وثبات الهوية حتى مع تغيير مرجع القيد. اختُبرت كذلك قاعدة استعادة SQLite منفصلة عند تغيير الرقم أو الإجمالي وبقاء القاعدة الحالية مفتوحة، وسحب سحابي محاكى مرفوض دون تغيير الحالة أو المراجعة، وتعديل حقيقي يغير الضريبة بقيد عكسي وبديل ثم يدمج تغييراً وصفياً مستقلاً. الاختبار الأساسي فشل قبل الإصلاح ونجح بعده.
- **حدود مهمة:** اختلاف مرجع القيد ليس دليلاً على صحته، ولا يثبت هذا الحارس وجود عكس وبديل صحيحين أو أن القيد البديل يطابق كل بيانات المستخلص؛ لا يزال تصميم تسلسل متعدد التعديلات وأدلة النسخ القديمة مطلوباً. يخص الحارس الختامي الموجود محلياً وعند استدعائه، وليس حماية لكل المستخلصات أو لكل كاتب أو تحققاً من الوارد كله. لا تثبت الاختبارات استعادة قاعدة العميل أو تزامن الأجهزة أو ذرية مخزني الإعدادات والبيانات. الحظر المالي والاعتمادات والمراحل الأصلية باقية.
- التحقق: 120/120 موجهة في ستة ملفات، ثم نجحت مجموعة موسعة بعد آخر إضافة تأكيد، وأنواع التطبيق والاختبارات و`lint:strict` والبناء (مع تحذير حجم الحزمة)، ومصفوفة المحرك 43/43، و`verify:all` ‏369/369. نجح `test:e2e` ‏4618/4618 في 566 ملفاً؛ ظهرت رسائل بيئة jsdom أثناء الاختبار. لم تُختبر بوابة GitHub لهذا الرأس أو Windows أو جهاز العميل، ولم يُنشر إصدار أو يُمنح اعتماد مالي.

### متابعة — إثبات انتقال قيد الختامي (جزئية للمراحل 1 و5)
- عالجنا ثغرة قبول معرف قيد بديل مختلق في لقطة واردة: عند تغير مرجع قيد ختامي محلي يفحص الحارس بقاء اليومية المحلية وسلسلة العكس والبديل لكل تعديل تالٍ، مع تفرّد الروابط وتطابق فرع العكس والسطور والأبعاد، وهوية كل قيد بديل وتسلسله، وربط آخر عكس بالمستند ومطابقة القيد البديل الأخير للأساس المالي وتاريخه. يسمح بسلسلة تعديلين حقيقيين، ويقبل عكساً تاريخياً محفوظاً كما هو قبل بداية المقارنة دون اختلاق أو إصلاح أدلة الماضي.
- اختبارات أولية كشفت قبول رقم قيد مختلق قبل الإضافة؛ وبعدها نجحت 146 حالة موجهة قبل إضافة اختباري استعادة وسحب. ترفض الاختبارات العبث بقيد وسيط أو عكسه وأبعاده وفرعه والمرجع الأخير وتاريخ المستند وإجمالي لا يطابق القيد، وتختبر دمج تعديلين فعليين مع إعداد مستقل. نجحت لاحقاً مجموعة 296/296 في 28 ملفاً، مع الأنواع وlint والبناء والمصفوفة 43/43 والاستعادة الملفية والسحب المحاكى.
- **الحدود:** الحراسة محافظة وتحتاج تتابع العكس والبديل المولّد من الكاتب الحالي؛ قد ترفض سجلات قديمة مختلفة تحتاج مراجعة. لا تفحص جميع تفاصيل الأساس الكمي أو صحة العقد والضرائب أو كل التعديلات الوسيطة، ولا تثبت صحة أدلة محلية سابقة أو جميع القيود الواردة أو الكتّاب. لا تجعل استعادة SQLite ذرية مع بقية المخازن؛ لم تُختبر أجهزة العميل أو Windows أو المزامنة الحقيقية. لا تفعّل تحصيلاً جزئياً أو رد مقدمة أو إعادة فتح؛ المراحل 1–5 باقية مفتوحة حتى استيفاء الأدلة والاعتمادات المذكورة في الخطة.

### حالة أول خمس مراحل بعد متابعة تسلسل الختامي
- **1 التخزين:** تحققت حماية تسلسل تعديل ختامي محلي حيث يستدعى الحارس؛ لا تزال معاملة الإعدادات والبيانات المشتركة، والكتّاب والأجهزة واستعادة العميل دون إثبات شامل.
- **2 الإشعارات:** الاختبارات الحالية تشمل حساب المقدمة وتاريخها والإشعارات الكمية وحدودها، لكن رد المقدمة الموجب لم يُفعّل؛ يحتاج ترحيل وتسوية كاملة وأدلة التقارير والضرائب والماكينة والتزامن واعتماداً.
- **3 المحتجز:** اختُبرت حسابات التخصيص الكامل والحراس؛ لا يوجد في هذه الجولة تمكين لعكس التحصيل أو تسويته أو التحصيل الجزئي والمتعدد، وتحتاج الأدلة القديمة غير الموزعة مراجعة مستقلة.
- **4 التوثيق والتحصيل المعقد:** اختُبرت حراسات نطاق التوثيق والخزينة والاسترداد؛ لا يثبت ذلك أدلة تصحيح ضريبي خارجي أو تسوية كل الفواتير المشتركة أو المدفوعات أو اعتماد الجهة.
- **5 إعادة فتح الختامي:** اختُبر تعديل الختامي مع بقاء طبيعته وسلسلة عكس قيده؛ إعادة الفتح والبديل بوثائق الحصر والمحتجز والمقدمات والصلاحية والسبب لم تُنفذ. لا تخلط تعديل الختامي بإعادة فتحه.
- الفحوص الحالية: 296/296 اختباراً موجهاً في 28 ملفاً تغطي أجزاء من التخزين والمقدمة والإشعارات والمحتجز والتوثيق والختامي؛ أنواع التطبيق والاختبارات و`lint:strict` والبناء ومصفوفة المحرك 43/43 نجحت. هذه ليست إكمالاً لخمس مراحل؛ جميعها تظل مفتوحة حتى تحقيق معاييرها. نجح `verify:all` ‏369/369 و`test:e2e` ‏4622/4622 في 567 ملفاً بعد التغييرات؛ ظهرت رسائل بيئة jsdom ولم تُختبر Windows أو جهاز العميل.

### متابعة — حماية الختامي في الحفظ العادي لسطح المكتب (المرحلة 1 جزئياً)
- كشف اختبار SQLite فعلي أن حارس الختامي كان يطبق في الاستعادة والدمج، لكنه لا يُستدعى عند حفظ لقطة غير متعارضة، فيمكن إسقاط علامة ختامي أو تغيير إجماليه مع إبقاء قيده، أو إسناده لقيد مختلق. فُصل فحص الختامي عن بقية تاريخ المقدمة والمحتجز، ووُصل بحفظ لقطة سطح المكتب عندما تتغير المستخلصات أو اليومية وكان ختامي موجوداً في اللقطة السابقة. لا يجبر ذلك على إعادة فحص أرصدة المقدمات القديمة غير المتغيرة.
- يرفض الحارس أيضاً عكس القيد المحلي الذي ما زال المستخلص يشير إليه دون ربط بديل. يقبل تعديلين مشروعين متتاليين، وتُرفض اللقطة المعطوبة قبل الكتابة وتبقى المراجعة واللقطة دون تغيير. فشل الاختبار قبل الإصلاح؛ نجحت 134 حالة موجهة في سبعة ملفات بعدها. نجحت أنواع التطبيق والاختبارات وlint والبناء والمصفوفة 43/43 لهذه الجولة؛ وأُضيف اختبار SQLite لرفض حفظ قيد معكوس دون ربط المستخلص ببديله ثم نجحت 26/26 موجهة.
- حماية كاتب `DesktopStateStorage` فقط ولا تشمل أي كاتب مباشر لقاعدة SQLite أو ويب/مزامنة غير مستدعٍ للحراس أو ذرية مخزن الإعدادات؛ لا تصحح سجلاً قديماً معطوباً ولا تثبت كل التسويات. لم تُنجز المراحل الخمس أو تُفعّل التسويات أو إعادة الفتح بناءً على ذلك.

### متابعة — تدقيق تجريبي لإشعار إعادة المقدمة (المرحلة 2 جزئياً)
- أُضيف إلى حارس إشعارات المستخلص وضع تجريبي صريح للنسخة 3 يراجع اختيار المقدمة المعادة وتوزيعها العكسي التراكمي، وكميات الإشعارات وضريبتها ومحتجزها وقيد كل منها، بما فيه رصيد 2109 ونصيب ذمة العميل. يبقى الحارس الافتراضي رافضاً لهذه النسخة، ولا يستدعي المسار التشغيلي الخيار التجريبي؛ لا تُرحّل مقدمة موجبة بهذا التغيير.
- اختبار يكوّن مستخلصاً ومقدمة حقيقيين ثم يبني إشعارين تجريبيين بقيدين مستقلين؛ يفحص الحارسين معاً ورفض تغيير التوزيع والكمية والمحتجز وقيد متزن بمبلغ مقدمة غير مطابق، ورفض النسخة عند غياب الخيار التجريبي. نجحت 31/31 في خمسة ملفات موجهة بعد الإضافة. نجحت أنواع التطبيق والاختبارات وlint والبناء والمصفوفة 43/43.
- الحد: هذا ليس إطلاقاً أو اعتماداً للمعالجة؛ لا يفحص الترحيل الفعلي أو كامل مسارات ذمم العميل/التقارير والخزينة والماكينة والنسخ والاستعادة، أو المعاملة والصلاحيات والمستندات المشتركة، كما لا يستبدل تدقيق سجل المقدمات والفروع الفعلي. المرحلة 2 مفتوحة حتى تكامل كل تلك المسارات واختبارها والاعتماد المالي.

### متابعة — تخطيط حصص تحصيل المحتجز (المرحلة 3 جزئياً)
- أضيف مخطط FIFO يحسب حصة تحصيل محدد ويعيد تشغيل التحصيلات السابقة ذات التوزيع المثبت بترتيب القيود، مع رفض نقص دليل قديم أو حصص مخالفة أو فائض على رصيد مستخلص أو تصادم معرف قيد. يراجع رصيد كل مستخلص عند وقت التحصيل ويتوقف إن جعل إشعار لاحق رصيد المستخلص أقل من المبلغ المحصّل عليه. لا يختلق تخصيصاً ولا يغيّر مدخلاته.
- ما زال `releaseRetention` يحظر وجود تحصيل سابق ويحصّل كامل الرصيد فقط؛ يستخدم المخطط في هذه الحالة لتأكيد نفس حصص التحصيل الكامل، ولم يُفعّل تحصيل جزئي أو عكس. نجحت 78/78 في تسعة ملفات تشمل المخطط والحالات السابقة والواجهة، والأنواع وlint والبناء والمصفوفة 43/43 نجحت بعد الإضافة.
- المخطط لا يثبت قيود التحصيل وتواريخه وصلاحية الخزينة أو الماكينة أو الاعتماد، ولا يحقق تدقيق الاستعادة والتزامن أو معالجة إشعار بعد تحصيل سابق. لا تعتبره تنفيذ المرحلة 3 أو ترفعه إلى التشغيل الجزئي دون تلك المعالجة.

### متابعة — حماية جدول الكميات بعد الختامي (المرحلة 2 جزئياً)
- اختبار جديد فشل قبل المعالجة لأن إضافة بند وتغيير هويته كانا يمران مباشرة. كاتب جدول الكميات يرفض الآن إضافة أو حذف بند وتغيير الكمية والسعر والوحدة والتقدم بعد صدور ختامي في المشروع؛ يبقي التعديل الوصفي ومشاريع أخرى متاحة. التعديل يرفض أيضاً الحقول غير المصرح بها مثل المعرّف والمشروع والتقدم، ويتحقق من تكلفة التقدير والتقدم العددي. تعطّل الواجهة الإضافة والحذف والتقدم وتشرح السبب؛ تعرض أخطاء الحراسة بدلاً من استثناء غير معالج.
- نجحت 42/42 في سبعة ملفات والأنواع وlint والبناء والمصفوفة 43/43. فشلت بوابة واحدة من 369 لأن سجل العمليات الصامتة كان لا يزال يسرد تحديث التقدم؛ أزيل الإدراج القديم ونجحت البوابة منفردة، ثم نجح الشامل 369/369. الحراسة على الكتّاب المباشرين فقط؛ لا تثبت حماية كل مسارات الاستيراد والدمج أو أفعال الباطن أو تعديل تقدير التكلفة، ولا تنفذ إعادة فتح الختامي؛ لا تعدّ المرحلة مكتملة.

### متابعة — حفظ أساس الكميات عند الاستعادة والتزامن (المرحلتان 1 و5 جزئياً)
- أظهرت الاختبارات قبل الإصلاح إمكان تغيير جدول الكميات بعد ختامي في لقطة محفوظة رغم حظر الكاتب المباشر. يحمي حارس تاريخ الختامي الآن البنود المحلية الموجودة: إضافة أو حذف أو نقل بند، وتغيير الكمية والسعر والوحدة والفرع ورابط أمر التغيير أو التقدم بلا تعديل ختامي مثبت؛ يقبل الوصف ومشروعاً آخر. يفحص تغيير التقدم في تعديل مثبت مقابل سطر الختامي الجديد أو نسبة البند السابقة عند إزالته. يعمل ذلك في فحوص الاستعادة والسحب والدمج، والحفظ غير المتعارض عبر `DesktopStateStorage` حين تتغير المجموعة.
- نجحت 122/122 في ثمانية ملفات، تشمل حفظ SQLite حقيقياً وإعادة فتحه وتعديل حصر ختامي فعلي، ورفض نسخة قاعدة وسحب سحابي محاكى. كانت أول محاولة تطبيق قد ربطت `else` بشرط خاطئ وفشلت اختبارات التعديل والعكس؛ صُحح الربط وأعيدت الاختبارات. نجحت أنواع التطبيق والاختبارات وlint والبناء والمصفوفة 43/43؛ ونجح `test:e2e` ثم `verify:all` ‏369/369.
- لا يُختلق جدول إذا لم يكن محفوظاً محلياً، ولا يتحقق الحارس من كل بيانات البنود أو القيمة التعاقدية وصحة جميع التعديلات الوسيطة أو كل الكتّاب وتزامن الأجهزة. قد يرفض حالات قديمة ملتبسة للمراجعة. لم تُنفذ إعادة فتح الختامي أو تُغلق المرحلة الأولى أو الخامسة، ولا يثبت هذا معيار المراحل الخمس.
- أضيف بعد الشامل اختبار دمج لقطات متزامنة في الاتجاهين: صدور ختامي في لقطة مع تغيير كمية أحد بنوده في أخرى مرفوض؛ نجح الملف 10/10. هذا ليس اختبار أجهزة فعلية.
