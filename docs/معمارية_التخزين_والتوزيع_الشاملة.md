# معمارية التخزين والتوزيع الشاملة — «تَحَكَّم» على ثلاث مراحل

> **وثيقة قرارات معمارية** أُعدت بطلب المالك قبل كتابة أي كود (§101) — تغطي الانتقال من
> تخزين localStorage الحالي إلى: قاعدة SQLite محلية داخل حزمة EXE، ثم محل واحد بعدة
> أجهزة (لحظي)، ثم فرعان بعشرة أجهزة على قاعدة موزعة (محلي أولاً، ومركز تجميع للفروع).
>
> **القرارات المحسومة من المالك (مسجلة ولا تُنقض إلا بقرار موثق مثله):**
> 1. داخل المحل الواحد: التزامن بين الأجهزة **لحظي (ثوانٍ)**.
> 2. بين الفروع: **مركز تجميع مشترك** (يبدأ لاحقاً على VPS) — مع بقاء الحفظ **محلياً أولاً**.
> 3. الترتيب: **التصميم الشامل أولاً** (هذه الوثيقة) ثم التنفيذ مرحلةً مرحلة.
>
> **المرجعية القائمة:** 262 بوابة تحقق (245+17 رحلة) · 510 اختباراً في 100 ملف ·
> مصفوفة المحرك 220 مسار ترحيل · كل المبالغ أعداد صحيحة بالقروش.

## ١) أين نقف اليوم — الحقيقة بلا تجميل

| الطبقة | الوضع | الحكم |
|---|---|---|
| بيانات الإنتاج | `zustand persist` → **localStorage** (`shopsys-data` + `shopsys-app`) | يضيع بمسح بيانات المتصفح · سقف ~5-10MB · جهاز واحد |
| demo.sqlite | بيانات الأنشطة التجريبية (DEV فقط، 35 جدولاً) | ليست قاعدة إنتاج — لكنها خبرة SQLite قائمة |
| المستخدمون والصلاحيات | `appUsers`/أدوار/صلاحيات فعالة/بوابة اعتماد المستندات | **موجودة وجاهزة لتعدد المستخدمين** |
| الفروع والمخازن والماكينات | `branches` · مخزن لكل فرع · ماكينة دفع لكل فرع · مراكز تكلفة | **النموذج بُني متعدد الفروع منذ البداية** |
| النسخ الاحتياطي | صفحة نسخ JSON ببصمة + لقطة تلقائية كل ساعة (القرار 28) | يخفف الكارثة ولا يمنعها |
| فلسفة الكتابة | «لا تعديل صامت» — كل تصحيح بقيد عاكس · حارس مركزي `assertJournalIntegrity` يرفض القيد المختل بأكمله | **أنسب طبيعة بيان ممكنة للتوزيع لاحقاً** |

**الخلاصة:** المنطق المحاسبي كله (13,400+ سطر في `repo.ts`) متزامن ومحروس ببوابات —
وهذه ميزة معمارية سنحميها في كل مرحلة: **البوابات تظل تعمل كما هي، ويتبدل ما تحتها فقط**.

## ٢) المبادئ الحاكمة للمراحل الثلاث

1. **محلي أولاً دائماً:** كل عملية تلتزم محلياً (transaction محلية) قبل أي إرسال لأي مكان.
2. **كاتب واحد لكل ملف:** لا يفتح ملف SQLite أبداً أكثر من عملية واحدة. (مشاركة الملف
   على شبكة SMB/NFS **مرفوضة** — تحذير الفساد الرسمي في وثائق SQLite.)
3. **البيانات تُنشأ ولا تُعدّل:** الفاتورة والقيد والسند مستندات تُنشأ؛ التصحيح بقيد عاكس
   (وهذا سلوك المحرك القائم أصلاً — نعمّمه كقاعدة توزيع).
4. **الأرصدة تُحسب ولا تُزامن:** أي رصيد (عميل/مورد/مخزون/خزينة) مشتق من القيود والحركات
   — المزامنة تنقل المستندات فقط، والأرصدة تُشتق محلياً عند كل طرف.
5. **الحارس عند الكاتب:** كل بوابة تحقق (`assertJournalIntegrity` وأخواتها) تعمل في
   المكان الذي يكتب القاعدة — لا يثق طرف أبداً بكتابة طرف آخر.
6. **معرّفات عالمية فريدة من اليوم الأول:** قرار مرحلة §101 يُصمم لصالح §103 (انظر §3.4).
7. **الهجرة باتجاه واحد فقط:** localStorage → SQLite مرة واحدة، ثم لا عودة. أي تحديث
   مستقبلي يرقّي المخطط داخل SQLite بترحيلات مُنمَّطة ومحروسة بنسخة احتياطية قبلية.

## ٣) المرحلة §101 — القاعدة المحلية + حزمة EXE + التحديث التلقائي

**الهدف:** جهاز واحد يعمل بملف قاعدة متين، حزمة NSIS مثبتة، تحديث تلقائي من GitHub.

### 3.1 المعمارية

```
┌─ Electron ──────────────────────────────────────────────┐
│  Renderer (نفس تطبيق Vite الحالي — dist)                │
│     │  نفس واجهة useDataStore/useAppStore حرفياً        │
│  Preload (contextBridge)                                │
│     │  جسر shopsysPrint (الكود بانتظاره) + storage IPC  │
│  Main                                                   │
│     │  better-sqlite3 ← ملف userData/shopsys.db (WAL)  │
│     └─ electron-updater ← GitHub Releases (latest.yml)  │
└─────────────────────────────────────────────────────────┘
```

- **المحرك:** `better-sqlite3` (متزامن — نفس نمط الكود الحالي، وprebuilds جاهزة
  لإليكترون). `node:sqlite` بديل بلا اعتماديات لكنها تجريبية وتوفرها في Electron رهن
  إصداره — لا نراهن عليها لبيانات عملاء.
- **القاعدة:** `userData/shopsys.db` بوضع `WAL` + `PRAGMA foreign_keys` +
  `integrity_check` عند كل إقلاع + `busy_timeout`.
- **المستودع يبقى واحداً:** `repo.ts` كما هو؛ يتغير **محلّ التخزين** فقط عبر نفس واجهة
  zustand (تنفيذاً لتعليق `app.store.ts`: «اليوم localStorage — غداً SQLite عبر نفس
  الواجهة»).

### 3.2 مخطط التخزين (المرحلة الأولى: جدول لكل مجموعة)

```sql
-- لكل مجموعة بيانات في المتجر (sales, journal, customers, ...)
CREATE TABLE journal (
  id INTEGER PRIMARY KEY,          -- Snowflake (انظر 3.4)
  payload TEXT NOT NULL,           -- JSON الكائن كما هو في الحالة اليوم
  origin_device TEXT NOT NULL,     -- جهاز المنشأ (توافق أمامي مع §103)
  origin_branch TEXT NOT NULL DEFAULT '',
  updated_at TEXT NOT NULL,
  seq INTEGER                      -- عمود فهرسة للترتيب
);
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);   -- الإعدادات ومفاتيح الحالة
CREATE TABLE migrations (id INTEGER PRIMARY KEY, at TEXT);
CREATE TABLE sync_outbox (...);    -- تُنشأ فارغة الآن — تُشغَّل في §103
```

- الكتابة **انتقائية** (المجموعة المتغيرة فقط) بدل لقطة الحالة الكاملة — يكسر سقف
  الحجم ويجعل التحديث التفاضلي طبيعياً.
- المرحلة الثانية من المخطط (لاحقاً وانتقائياً): تسطيح الجداول الساخنة (اليومية) إلى
  أعمدة حقيقية حيث يفيد التقارير — **لا نفعله الآن** حتى لا نخاطر بالبوابات.

### 3.3 النسخ الاحتياطي والترحيلات

- `userData/backups/`: أجيال دوّارة (ساعي يحتفظ بـ24، يومي بـ30، أسبوعي بـ12) عبر
  Backup API الرسمية (نسخة ساخنة بلا إيقاف).
- **قاعدة صارمة: نسخة احتياطية إلزامية قبل تنفيذ أي ترحيل مخطط** — التحديث التلقائي
  قد يصل مع ترحيل، فالترتيب دائماً: تحديث → نسخة → ترحيل → فحص سلامة → إقلاع.
- زر استعادة من داخل التطبيق (صفحة النسخ القائمة تُعاد توظيفها بصيغة `.db` إضافة
  لصيغة JSON القائمة للهجرة).

### 3.4 قرارات التوافق الأمامي — تُتخذ الآن ولا تُندم لاحقاً (الأهم في الوثيقة)

| القرار | الآن (§101) | ثم (§102/§103) |
|---|---|---|
| **المعرّفات: Snowflake 64-bit** (مللي ثانية 41 + جهاز 10 + تسلسل 12 — آمنة تحت 2⁵³ في JS و64-bit في SQLite) | كل صف جديد بعد الهجرة يأخذ معرّفاً فريداً عالمياً؛ المعرّفات الصغيرة القديمة تبقى كما هي (لا تصادم: قيم Snowflake فلكية الحجم) | فرعان ينشئان صفوفاً في نفس اللحظة بلا أي تصادم |
| **ترقيم المستندات لكل فرع** (`INV-A-2026-0001`) | نحتفظ بالشكل الحالي للجهاز الواحد + فهرس فريد يسمح مسبقاً بعمود الفرع | القيد الفريد يصبح (فرع، نوع، رقم) — بلا إعادة ترحيل |
| **أعمدة النسب** origin_device/origin_branch/updated_at على كل جدول | تُكتب منذ أول يوم | أساس دمج §103 وقاعدة «التعديل عند أصله» |
| **لا حذف أبداً** — إبطال/عكس فقط | سلوك المحرك القائم يُعمَّم كقاعدة طبقة التخزين | الدمج بين الفروع لا يفقد أثراً |
| **outbox فارغة جاهزة** | الجدول يُنشأ في المخطط من اليوم الأول | §103 يشغّلها بلا ترحيل |

### 3.5 الهجرة لمرة واحدة

أول إقلاع للـEXE: يقرأ `localStorage` (لو وجد من تجربة متصفحية) → يتحقق من البصمة
(checksum بنفس صيغة `core/backup.ts`) → يستورد داخل transaction واحدة → نسخة احتياطية
من الأصل قبل المساس → لا يعود للمتصفح أبداً.

### 3.6 الحزمة والتحديث (كما اتفقنا في §99/§100)

- `electron-builder` target `nsis` (واجهة تثبيت عربية) + نشر GitHub Releases.
- `electron-updater`: فحص عند الإقلاع + زر يدوي «تحقق من التحديثات» + تنزيل خلفي
  تفاضلي (blockmap) + تثبيت عند الإغلاق. ترقيم semver صارم في `package.json`.
- **توقيع الكود:** اختياري تقنياً للتحديث — بدونه تحذير SmartScreen لأول تثبيت فقط،
  والتحديثات اللاحقة تصمت. يُوصى بشهادة عند اتساع قاعدة العملاء.

### 3.7 معايير قبول §101 + البوابات الجديدة

- EXE يُثبَّت على ويندوز نظيف، القاعدة في userData، ومسح «بيانات المتصفح» لا يمس شيئاً.
- تحديث من إصدار 1.0.0 → 1.0.1 عبر GitHub Release يثبّت نفسه مع ترحيل آمن.
- بوابات جديدة: `verify_sqlite_storage` (المخطط + المعرّفات Snowflake + الترحيلات
  المؤمنة بنسخة قبلية + فحص السلامة) · `verify_local_migration` (رحلة هجرة
  localStorage → SQLite ببيانات حقيقية ثم مقارنة أرصدة طرف بطرف) · رحلة مستخدم
  `user_journey_exe_update`.
- **كل البوابات الـ262 القائمة تمر بلا تعديل** — معيار نجاح المرحلة نفسه.

## ٤) المرحلة §102 — مضيف المحل: 5 أجهزة لحظياً على قاعدة واحدة

**الهدف:** كاشير×3 + محاسب + صاحب محل — كل التغييرات تظهر عند الجميع خلال ثوانٍ.

### 4.1 المعمارية (نمط POS الكلاسيكي المجرب)

```
[جهاز المضيف — واحد فقط يلمس الملف]
  التطبيق الكامل + repo.ts + كل البوابات + SQLite
        │ WebSocket (شبكة المحل — واي فاي/سويتش)
        ├── كاشير 1 ─┬─ لقطة أولية عند الدخول ثم رقع لحظية
        ├── كاشير 2 ─┤─ كل تعديل = نداء RPC ينفذه المضيف وحده
        ├── كاشير 3 ─┤─ الطباعة من جهاز العميل نفسه (iframe print قائم ✓)
        └── المحاسب ─┘
```

### 4.2 حدود النقل — كيف تبقى الواجهة والبوابات كما هي

- ندخل **`DataTransport`** خلف واجهة المتجر نفسها:
  - `LocalTransport` (اليوم): ينفذ في العملية مباشرة — سلوك §101 بلا تغيير.
  - `RemoteTransport` (عميل الشبكة): كل نداء دالة مستودع يصبح RPC للمضيف، وكل رقع
    حالة تصل للمشتركين كبث.
- **المضيف ينفذ العملية كاملة بحراسة مركزية** (الحارس + بوابة الاعتماد + الصلاحيات
  الفعالة) — العميل يستقبل رسائل الرفض العربية نفسها ليعرضها كما لو كانت محلية.
- حجم البث: رقعة لكل عملية (المجموعات المتغيرة فقط)، لا لقطات كاملة بعد الدخول الأول.
- التعارضات **لا تولد أصلاً**: كاتب واحد متسلسل (better-sqlite3 متزامنة = تسلسل طبيعي).
- المصادقة: شاشة دخول على الأجهزة بمستخدمي `appUsers` القائمين — والصلاحيات تُفَعَّل
  عند المضيف لكل مستخدم (الكود القائم: `effectivePermissionsFor` + قفل الخزائن
  `treasuryAccess`).
- الاقتران: QR/رمز مضيف + توكن جهاز، والاستماع على الشبكة المحلية فقط.

### 4.3 حالات الفشل

| الحالة | السلوك |
|---|---|
| انقطاع عميل عن المضيف | يظهر شريط «انقطع الاتصال» + تعطيل الكتابة — القراءة من آخر لقطة |
| سقوط المضيف | المحل كله يتوقف (مصدر حقيقة واحد — مقبول وموثق للمالك) + إعادة تشغيله تعيد الجميع خلال ثوانٍ من اللقطة |
| تحديث المضيف | الأجهزة تستمر من لقطاتها حتى يعود — ثم تلحق بالرقع |

**سؤال مؤجل للمالك:** هل يُخصَّص جهاز صغير دائم التشغيل كمضيف، أم مضيف = جهاز الصاحب؟
(يؤثر على إجراءات «تبديل المضيف» — سنوثّق تشغيله السريع من نسخة احتياطية بأي حال).

### 4.4 معايير قبول §102 + الأدلة

- 5 أجهزة متزامنة: بيع كاشير يظهر في شاشة المحاسب خلال ≤ 3 ثوانٍ.
- بوابة اعتماد المستندات تعمل عبر الشبكة (طلب اعتماد من كاشير يصل لصاحب المحل فوراً).
- بوابات جديدة: `verify_lan_transport` (ترتيب الرقع وحتمية البث) · رحلة مستخدم
  `user_journey_lan_day` (يوم محل كامل بخمسة أدوار).
- **كل البوابات القائمة تمر عبر LocalTransport بلا تعديل** — ونفس الاختبارات تُشغَّل
  ثانية عبر RemoteTransport في وضع محاكاة داخل الاختبار.

## ٥) المرحلة §103 — فرعان، 10 أجهزة، مركز تجميع، محلي أولاً

**الهدف:** فرع (أ) وفرع (ب) — كلٌّ منهما §102 كاملة تعمل offline — وطبقة مزامنة عبر
مركز مشترك (لاحقاً VPS) والقاعدة المجمعة واحدة منطقياً.

### 5.1 لماذا مركز تجميع Outbox وليس CRDT (cr-sqlite)؟ — التعليل المحاسبي

CRDT يمنح «كل طرف يكتب دائماً ويندمج لاحقاً» لكنه **يُضعف الثوابت وقت الكتابة**:
لا يمكنه فرض قيد فريد متسلسل أو قيد مزدوج متوازن عالمياً لحظة الإنشاء. برنامجنا
محاسبة أولاً — **التسلسل والثوابت فوق كل شيء**. وبياناتنا بطبيعتها «تُنشأ ولا تُعدَّل»،
فالدمج عبر مركز بترتيب صريح أبسط وأكثر قابلية للتدقيق (كل حدث له موضع مؤكد في السجل).
لهذا: **نمط Outbox مع مركز ترتيب** — وهو القرار الذي اختاره المالك أصلاً.

### 5.2 المعمارية

```
فرع أ: مضيف + SQLite (outbox محلية)      فرع ب: مضيف + SQLite (outbox محلية)
   يعمل كاملاً offline دائماً                يعمل كاملاً offline دائماً
        │                                        │
        └────────► [المركز — Node + Postgres على VPS لاحقاً] ◄──────┘
                      سجل أحداث مرتب + مؤشرات تقدم كل جهاز
                      (الحمولة مشفرة بمفتاح الفرع — المركز يرى نصاً مشفراً)
```

### 5.3 نمط Outbox — الضمانة المحلية أولاً

- كل معاملة أعمال (فاتورة/قيد/سند/مرتجع…) تكتب **في نفس الـtransaction المحلية**
  (أ) الصفوف في جداولها و(ب) حدثاً في `sync_outbox` — لا مشكلة الكتابة المزدوجة أبداً.
- عامل مزامنة خلفي: يدفع الأحداث المعلقة للمركز (مع توكن الجهاز)، ثم يسحب أحداث
  الآخرين منذ مؤشره — الترتيب النهائي يحدده المركز (طابع تسلسلي مركزي).
- **الدمج عند كل فرع:** المستندات الجديدة تُدرج كما هي (معرّفات Snowflake لا تتصادم)؛
  الأرصدة تُشتق محلياً من القيود المجمعة (المبدأ 4)؛ التعديل مسموح **عند أصله فقط**
  (قاعدة origin_branch) — والتصحيح عبر الفرع الآخر يتم بقيد عاكس (فلسفة المحرك
  القائمة نفسها).

### 5.4 القواعد التفصيلية للدمج

| المجال | القاعدة |
|---|---|
| القيود والفاتورة والسندات | إلحاقية — تسافر كما هي وتُدرج بلا تعديل |
| الأرقام المتسلسلة | لكل فرع سلسلته (`INV-A-…`/`INV-B-…`) — الفهرس الفريد (فرع، نوع، رقم) يضمنها |
| المخزون | حركة لكل مخزن، والمخازن تابعة للفروع أصلاً في النموذج — التوزيع بين الفرعين بمستند **تحويل مخزني** (الموجود قائماً) موسوع بنسبة الفرعين |
| الخزائن والبنوك | لكل فرع خزائنه؛ التحويل بين فرعين = سند تحويل بين خزينتين بنسختين متقابلتين موسومتين (نفس دلالة `postTransfer` القائمة موسوعة) |
| العملاء والموردون المشتركون | بطاقات مشتركة تُزامن؛ رصيد العميل يُشتق من قيوده في الفرعين معاً (كشف موحد) |
| التعارض الوحيد الممكن (تعديل نفس البطاقة في فرعين) | قاعدة فحوى: آلية الدمج تُبقي الأحدث بترتيب المركز وتوثق الآخر في سجل تدقيق المزامنة — لا فقدان صامت أبداً |
| ساعة الأجهزة | لا يُثق بساعات الأجهزة — الترتيب مركزي حصرياً |

### 5.5 الأمان

- TLS إلزامي + توكن جهاز لكل مضيف (إصدار/إبطال من شاشة إدارة عند المالك).
- **تشفير حمولة الأحداث بمفتاح عمومي للفرع** — المركز (VPS) يخزّن نصاً مشفراً ولا
  يستطيع قراءة أرقام العملاء (نقطة بيع قوية للمالك) — المفاتيح عند الأجهزة فقط.
- عزل فرعي صارم في المركز + سجل تدقيق كامل لكل دفعة مزامنة.

### 5.6 معايير قبول §103 + الأدلة

- فرعان يعملان offline يوماً كاملاً، ثم الاتصال: لا قيد مفقود ولا مكرر ولا ميزان
  مختل — ميزان موحد متوازن على البيانات المدمجة.
- بيع في الفرع أ يظهر في تقارير الفرع ب خلال ≤ 60 ثانية عند توفر الاتصال.
- سقوط المركز: الفرعان يكملان العمل (محلي أولاً) ويلحقان عند عودته.
- بوابات جديدة: `verify_outbox_exactly_once` (لا حدث يُرسل مرتين ولا يُفقد) ·
  `verify_branch_merge` (محاكاة فرعين في نفس العملية: كتابة متزامنة ثم دمج ثم
  ميزان متوازن وأرقام بلا تصادم) · `verify_sync_security` (توكن + تشفير) · رحلة
  `user_journey_two_branches`.

## ٦) التوافق مع منظومة الجودة القائمة — القاعدة الذهبية للتنفيذ

> **كل بوابة من البوابات الـ262 وكل اختبار من الـ510 يجب أن ينجح في كل مرحلة دون
> تعديل منطقه — ما يتغير هو «أين» تنفذ الطبقة تحتها.** أي مرحلة تكسر بوابة قائمة
> فهي خطأ تصميم في المرحلة، لا في البوابة.

| الأصل القائم | مصيره |
|---|---|
| `repo.ts` (المنطق كله) | لا يمس — طبقة النقل/التخزين تحته فقط |
| البوابات المحاسبية (مصفوفة المحرك 220 مساراً) | تعمل عند الكاتب (المضيف) في كل وضع |
| اختبارات jsdom | تُشغَّل على LocalTransport دائماً + نسخة عبر RemoteTransport محاكى في §102 |
| صيغة النسخ JSON (`core/backup.ts`) | تبقى للتصدير اليدوي + تُضاف صيغة `.db` للنسخ الدوّارة |
| demo-db | تصبح استيرادها المباشر تافهاً (نفس المحرك) |

## ٧) البدائل المرفوضة — ولماذا (حتى لا تُعاد مناقشتها)

| البديل | سبب الرفض |
|---|---|
| مشاركة ملف SQLite على مجلد شبكي (SMB/NFS) | تحذير فساد رسمي — ممنوع نهائياً |
| PostgreSQL/MySQL على أجهزة العملاء | خادم وصيانة لعميل محل واحد — تعقيد بلا مبرر |
| IndexedDB/Dexie | ليست قاعدة حقيقية — لا transactions بمستوى القيد المزدوج، وبقية في رحمة «مسح بيانات الموقع» |
| CRDT (cr-sqlite) للتوزيع بين الفروع | يُضعف الثوابت وقت الكتابة — محاسبياً الترتيب والقيد المتوازن فوق كل اعتبار |
| مزامنة القيعان (replication على مستوى الملف) | تنقل كل شيء ولا تحترم دلالات المستندات — outbox الدلالي أدق وأرخص |
| RDP/سطح مكتب بعيد للأجهزة | تجربة سيئة لخمسة مستخدمين متزامنين |

## ٨) أسئلة مؤجلة للمالك (لا تعيق المراحل)

1. جهاز المضيف: جهاز الصاحب أم mini-PC مخصص؟ (تشغيل إجراء «تبديل المضيف» من نسخة).

## ٩) خارطة التنفيذ ومعالم القبول

| المرحلة | النطاق | معلم القبول الرئيس |
|---|---|---|
| **§101** | SQLite محلية + هجرة localStorage + EXE/NSIS + تحديث تلقائي GitHub + معرّفات Snowflake وترقيم لكل فرع وأعمدة النسب (توافق §103) | EXE على ويندوز نظيف؛ مسح بيانات المتصفح لا يمس؛ تحديث تلقائي مثبت؛ 262 بوابة قائمة + بوابات المرحلة خضراء |
| **§102** | DataTransport + وضع المضيف + WebSocket رقع لحظية + دخول متعدد بصلاحيات قائمة + طباعة من الأجهزة | 5 أجهزة، انتشار ≤ 3 ثوانٍ، بوابة الاعتماد عبر الشبكة، لا تعارضات (كاتب واحد) |
| **§103** | Outbox + مركز Node/Postgres + دمج فرعين + ترقيم لكل فرع + تشفير حمولة + أوضاع offline | فرعان offline يوم كامل ثم مزامنة: ميزان موحد متوازن، لا فقدان ولا تكرار، سقوط المركز لا يوقف الفرعين |

**ترتيب صارم:** لا تبدأ مرحلة قبل خضوع سابقتها لمعالم قبولها كاملة — الأساس المتين
أولاً، والتوزيع يُبنى فوقه ولا يُسابقانه.
